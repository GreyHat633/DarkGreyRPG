## 2. 已发现问题：先定位与复现，再施工

### 2.1 WP-A 的已核实调用链

固定基线中，`CanonicalStoryEventAdapter.onPlayerTick()` 每 10 tick 对每位服务端玩家调用媒体同步、待接续恢复、区域匹配与区域处理。相应入口创建 `Context`，进而创建 `CanonicalStoryServerService`；其构造函数无条件执行 `data.bindAvailable(...)`。[S06—S09]

`CanonicalSessionSavedData.bindInternal()` 会取全量快照、新建 Session／Story 容器，执行 Session NBT 编解码与实例恢复，并替换容器。即使 `pendingRaw == null`，也存在这条重建路径；`CanonicalSessionInstanceStore.snapshots()` 遍历并排序整个存储集合。[S09][S10]

**已知的是重复工作结构，不是实测严重程度。**本版须测出正常轮询里全量恢复次数、处理实例数、分配量与耗时。不得把内存 NBT 转换描述成每次从磁盘加载整个 Minecraft 世界。

### 2.2 WP-B 的已核实断路

`recoverPendingRoutes()` 检测到待接续记录后调用 `route(player, current, null)`，而 `route()` 开头因 `first == null` 直接返回。后面的 `recoverPendingTerminalRoutes(...)` 因而无法通过该入口执行。[S07]

这是待接续自动恢复入口的逻辑问题；不代表所有重连、所有对话或玩家移动必然卡住。P0 必须保留一个合法待接续样例，证明生产入口的前后差异，不能只直接调用底层恢复函数让测试通过。

### 2.3 WP-C 的已核实结构与待验证影响

`MainThreadScheduler` 使用静态无固定容量队列，在 tick START 中排空，并直接运行 `task.run()`；调度层没有每 tick 预算和逐项失败处理。[S11]

部分生产者已经限流，例如媒体拥有速率、在途数量与后台队列限制；不能一概称所有消息无界。[S12]

需要补的不是“丢掉超额任务”或“捕获所有异常就好”，而是完整的接收、等待、执行、拒绝／取消与资源释放合同。客户端与服务端分别处理，不混用世界或连接身份。

### 2.4 周边热点按证据排查，不预先判罪

`CanonicalTaskForgeManager` 中若干路径先取整库快照后按玩家过滤；Task 展示会周期性投影；跨 Story Logic 求值和 Session Logic 查询也可能与图规模相关。[S13][S14]

只对 P0 计数／剖析证实有明显贡献的热点做定点索引、缓存或避免无效计算。不能因为看到循环就全改，也不能没有测量就重写整个求值器。

## 4. WP-A：正常运行时不重复全量重建

### 4.1 绑定触发条件

首次有效 pending 数据恢复、真实资源快照／代次变化、存储对象替换等才触发必要重绑。仅创建 service wrapper、普通区域轮询、媒体同步、只读查询或恢复检查，不得无条件重新编码／恢复全世界实例。

必须显式区分：

| 情形 | 要求 |
|---|---|
| 同世界、同有效资源快照、已完成绑定 | 复用当前实例；普通轮询完整重绑次数为零 |
| 首次合法 pending | 正常恢复，不能因缓存而永远停在未绑定 |
| 同世界资源代次真正变化 | 失效并按当前 reload／包资格合同重建必要部分 |
| 内容未变化 reload | 不重置 run、transport、收据或已选择状态；若项目对象换了，也不得每次后续轮询继续重建 |
| 世界卸载／新服务器生命周期 | 老缓存无效；新世界首次绑定独立进行 |
| 跨维度但仍同一个权威世界存储 | 不把维度变化误作新存档，不重置故事；定位规则仍按现行维度合同 |
| 读取失败／隔离对象 | 不以“缓存命中”绕开可读门禁，不恢复旧默认空对象 |

不能只检查 resolver 对象引用：当前调用者可能每次创建新 resolver；也不能只看一个永久 `isBound` 忽略资源版本。具体 key 应复用真实世界存储身份和项目快照／已有内容代次。**运行状态 revision 每次变化，不应成为重新解析整张资源图的理由。**

### 4.2 缓存与事务边界

保持主线程权威；不把 Minecraft 实体访问、库存更改、运行游标或 SavedData 修改扔到线程池。不可变资源结构可以复用，可变玩家状态不能共享。

若保留 service／context 缓存，其寿命必须与真实存储及内容代次一致，不能静态强引用住退出后的 integrated server／World／EntityPlayer。按当前卸载／停服事件释放；弱引用值若反向持有 key，不能宣称自然无泄漏。

必要重绑先构造并验证替代状态，再提交；保留有效 pending、无关玩家实例、历史与继续执行记录。失败不能留下部分新表配部分旧表。严禁清掉离线实例来降低基准开销。

### 4.3 每玩家索引及展示开销

测量显示 Task 快照／Journal／区域查询是热点时，优先按玩家／活动状态取相关实例，或复用已有索引、dirty generation；不要每位在线玩家复制全世界所有 Task 后才过滤。维护索引时覆盖创建、完成、取消、丢弃、重载、恢复、登录登出和死亡换实体。

资源结构校验与输入边界不能全部删除：可以在稳定资源进入当前代次时验证一次，再复用已验证结果；请求、状态与权限仍按需验证。

展示内容未变化时避免反复完整编码和发送；动态文本、时间相关输入和背包采样仍按现行语义更新。不得通过关掉同步、让计数不刷新或大幅延长交互间隔来“优化”。

### 4.4 必须增加的断言

- 初始化完成后，同一快照下至少 200 次生产级轮询：全量绑定次数不随轮询次数增长。
- 不以“只 new 一个 service 的单测”代替实际四条轮询调用；记录资源恢复次数、扫描实例数及对象分配热点。
- 一个真实资源代次变化后，恢复正确；之后回到稳定状态，不进入反复失效循环。
- 内容未改 reload 前后，玩家游标、完成锁存、transport／run 和库存／收据一致。
- 增加离线玩家存量时，不因每位在线玩家的纯查询反复恢复这些实例；正常保存仍保留全部记录。
- 世界 A 与 B 的相同 Story UID／玩家 UUID 不命中彼此缓存，反复进出后已退出世界不被长寿命缓存保活。

## 5. WP-B：自动接续与玩家脱困

### 5.1 修复生产入口，而非只让底层函数通过

`first == null` 应表示“当前没有额外的新 dispatch”，不能直接等同“没有待恢复工作”。可将网关构造与恢复提取成小的共用路径，或调整顺序；避免建立第二套并行恢复机制。

没有 pending 且没有 first 时应快速无操作。已有 pending 时，登录／定时恢复入口无需玩家额外点击，就能处理合法待接续。无关玩家、未授权的新启动或不合法目标不得因此被执行。

### 5.2 保留幂等、预算与等待语义

保持现有 terminal claim／target／applied 的持久语义：来源结束记录、目标 run、收据须对应。反复 tick、重复网络包、重连、无内容 reload 不得重复创建目标或重复发放 DGR 奖励。

处理自动路由与跨 Story Logic 时使用真实共享、有限的步骤预算；不能在内部每次递归重新发一份预算，绕过现有保护。预算消耗完要受控中止／延后或进入现行错误状态，保持清晰诊断，不每 tick 无限重试同一失败。

**固定次数预算不等于时间预算。**若一个单步本身很重，须修单步或按可验证语义拆阶段；不能靠更大 256／更大线程栈掩盖问题。

合法条件等待、媒体排队、等待玩家选择，不是运行线程死锁。必须区分“权威状态在等待”与“请求已发却无回应”。不得给条件等待统一加超时后自动选择／完成。

### 5.3 故障与卡住样例

| 输入／时点 | 验证内容 |
|---|---|
| A 已结束，A→B pending 存在，first 为空 | 登录／周期入口可以恢复 B，不要求点击其他角色 |
| B 已建立，来源尚未记 applied | 恢复同一目标，目标实例／奖励不重复 |
| pending 已应用 | 后续恢复无业务变更 |
| 目标暂不可用或按现行规则不能新启 | 明确等待／拒绝，不编造成功、不删 unrelated 状态、不高频刷日志 |
| 多条 pending、链与环、超预算 | 有限工作，普通服务器 tick 可继续；错误作用域准确 |
| 恢复时玩家断线／换实体／进入另一世界 | 不向旧连接发消息、不把原 world 的 cursor 写进新 world |
| Choice 请求过期／重复／被拒绝 | 回应或现有拒绝反馈终结 pending，客户端不会永久锁住按钮 |

对于任务控制台、会话窗口或其他输入等待，先复用已有拒绝／关闭／刷新通道。不得加入无身份校验的强制重试按钮或每秒重发奖励请求。外部任意 `/command` 的跨崩溃幂等能力不能被 DGR 收据虚构保证；本版不重做命令系统。

## 6. WP-C：主线程队列、过载与生命周期

### 6.1 先建立调用点清单

扫描所有 `scheduleServer`／`scheduleClient` 及相似队列入口，逐类记录：是否网络请求、后台 IO 回调、媒体上传、展示投影、业务变更或资源释放；拥有者是服务器实例、世界存储、连接、玩家／transport，还是跨世界可安全保留的纯缓存。

只处理 DGR 自有任务。保留现有媒体速率／在途预算；不解除这些限制后指望总队列兜底。新队列机制必须迁移实际调用者，不能只改 API 而漏掉取消责任。[S11][S12]

### 6.2 有界工作，不承诺抢占任意 Runnable

为服务端、客户端各设置可测试的每 tick 工作量／时间预算及队列准入边界。默认预算由 P0 实测冻结，作为内部工程参数，不增加用户控制台。

预算到达后，未执行的已接收任务留待后续 tick，不能静默丢掉。保持同一有序业务流的 FIFO 和既有操作因果顺序，防止某类流量饿死另一类；不同类的优先级只能在证明不改变顺序合同时使用。

时间预算只能约束任务之间，**不能强行抢占已经执行的 Runnable**。若单项任务超时，记录真实调用点并优化；禁止用 `Thread.stop`、中断主线程或在后台线程执行世界逻辑“修复”长任务。

### 6.3 满载、拒绝与取消的完整责任

可合并的只包括失效后可由最新状态完全替代的刷新请求；不可丢弃选择、提交、奖励、续接、事务完成或必要释放回调。需要减少流量时，优先在昂贵工作开始前限流，并给真实调用者明确的失败／重试结果。

凡因队列满、连接失效、世界退出、旧 epoch 或业务拒绝而不执行的任务，都要终结本任务所持的 in-flight、lease、pin、pending 标记和等待 UI。**清队列不等于释放资源。**

必须有测试证明媒体请求被取消后 `IN_FLIGHT` 不会永久占用、后台结果不会复活退役包、后续新世界还能下载。完成／释放任务的所有权不得因普通任务配额耗尽而泄漏；具体做法保持最小，不搭建通用事务调度平台。

### 6.4 错误边界

优先在拥有业务上下文的请求／任务边界处理可恢复异常：报告准确失败、保留 request／sequence、只隔离对应操作，继续允许其他无关任务执行。通用队列最后一层保护只能作为可观测的失败隔离，不得打印成功或隐藏损坏状态。

不要把 `Throwable`、`OutOfMemoryError`、`StackOverflowError` 全部吞掉后继续声称服务器健康。严重新故障应失败、留证、退出压测；调度保护不能承诺 JVM 已损坏时仍可安全运行。

异常日志按类别／对象合理限频，保留首次堆栈和累计次数，避免错误本身刷爆磁盘。测试版可输出采样摘要，不在生产每 tick 为每个玩家打完整状态。

### 6.5 世界、维度、连接与停止

四种情况必须分开：同一服务端内跨维度、同一客户端退出世界 A 再进 B、客户端断开服务器 X 再连 Y、死亡重生导致实体替换。服务器代理无缝跨服／额外多世界插件没有现成支持时，不在本版新增。

静态队列和后台结果需要进程内来源标识／epoch 或等效现有校验。不能仅按维度号 0、同一个玩家 UUID、Story UID 或文件名判断仍属于当前世界。控制数据必须核对来源世界／连接；内容哈希相同的只读媒体文件可复用，但授权、游标和 pending 不能复用。

跨维度仍处于同一存档时，不无差别取消所有事务。对涉及位置／实际实体的待提交请求重新核验；对世界存储级合法任务遵循其归属。

停止／卸载时停止接收旧来源的新业务，作必要取消与释放，后台晚到结果不能重新加入新生命周期。不能通过等待后台 Future／线程 join 阻塞服务器或渲染主线程。纯资源清理与主线程世界操作分开。

## 7. Codex 必须自行测试：证据层级与自动化要求

### 7.1 四种证据不能相互冒充

| 代码 | 层级 | 能证明什么、不能证明什么 |
|---|---|---|
| A | 纯逻辑／当前真实 Minecraft 类 Probe | 验证模型、编解码、路由、预算与不变量；不代表真实网络延迟或 FPS |
| S | 实际 Forge 服务器＋独立隔离驱动 | 验证生产 tick、保存重启、任务生成与服务调用负载；逻辑 UUID 不等于实际在线客户端 |
| N | 匹配正式 JAR 的真实网络客户端／完整协议客户端 | 验证连接、交错请求、实体交互和回应；无渲染协议客户端不能证明画面性能 |
| C | 实际 Minecraft 图形客户端 | 验证 GUI、输入、帧时间、媒体上传、场景退出；软件渲染／同机多开须单列 |

人工听音可作为另列 H 记录；不是本版阻塞整个服务器压力测试的先决条件。不能把播放日志写成人耳确认。[F01][S03]

### 7.2 不让用户承担可以自动完成的检查

Codex 自行：准备依赖和隔离目录、生成合法资源与负载、启动授权的测试进程、操作现有 UI／网络入口、运行固定种子序列、采样、分析、修复和复跑。只在确实缺少合法依赖、账号、图形环境或人工感知时集中提出一次具体需求；等待时继续可做的测试。

优先使用现有客户端自动操作／UIA、可用的正常测试账号、已有测试入口与隔离 driver。不能为凑人数写一套庞大机器人平台，也不能把被生产明确排除的 `FakePlayer` 当作真实玩家交互证明。使用合成 UUID、测试服务调用、完整网络客户端或图形客户端，各自计数并标注。

没有实际网络客户端条件，就记录对应 N／C 阻塞，不能将 A／S 的 32 个逻辑用户写成“32 人联网实测”。测试仍要完成服务器负载和核心断言。

### 7.3 生成器与可复现性

生成合法当前 schema、真实 ResourceAddress、完整 membership／引用闭包的测试资源。至少有一份通过当前 Studio 正常操作导出的 `.dgrs` 和一份 `.dgrs.g`，同字节进入最终运行样例。

规模数据可由测试生成器或正式服务接口产生，但须经过当前生产验证。区分 **资源数量、保存的实例数量、当前 ACTIVE 实例数、任务目标数、图节点／边数、实际事件率、网络玩家数**；这些指标不能用同一个“任务数”替代。

不得把 10000 行伪造 JSON、6500 条实体指名、10000 个没有被 tick／事件访问的空实例叫作“巨量任务同时运行”。不能为了生成规模样本放宽正式包边界；遇到现行预算限制，明确这是准入结果，或用多个合法包分摊，不能静默截断。

反例／故障样例与正常样例分开，不把手改包用于证明完整作者链。性能统计只统计实际成功创建和实际参与运行的对象，生成失败的记录不计入规模。

## 8. 默认负载梯度与持续运行

以下数值全部是**本版工程测试默认值**，不是承诺 DGR 已能承载这些规模。优先逐轴改变，再选择两个高风险因素叠加，不全量笛卡尔积。

### 8.1 梯度

| 轴 | 默认档位／要求 | 说明 |
|---|---|---|
| 逻辑用户 | 1、4、16、32 | A／S 可覆盖；与 N 实际网络人数分别记 |
| 真正联网玩家 | 至少 2；资源允许追加 4 或 8 | 至少两个不同玩家交错推进且可分别观察回应；缺条件为 BLOCKED |
| 世界内 ACTIVE Task 实例 | 10、100、1000；扩展尝试 5000 | 分布到多个合法 Story／placement／逻辑玩家；5000 是找拐点，不保证该档达标 |
| 离线仍保存实例 | 0、1000、10000 | 与在线活跃量解耦，验证离线存量不会被每次轮询全量恢复或删除 |
| 图复杂度 | 约 20、100、300 节点，并记录边数 | 区分宽图、长链、合法等待和应拒绝的环；不要只有空目标 |
| 操作节奏 | 空闲、固定频率交互、2 倍／4 倍短突发 | 高频请求以当前生产允许／拒绝结果计，不绕过限流 |
| 生命周期 | 同进程世界 A↔B 至少 20 次；跨维度往返至少 20 次；断连重连至少 10 次 | 至少一组在后台媒体／任务尚未完成时切换 |

先跑低档，验证生成器与测量器正确，再升档。内存逼近上限、队列持续不降或 tick 长时间失去响应时保留现场并停止升压；不是必须把测试机耗尽才算认真测过。

### 8.2 三组核心规模实验

**空闲实验：**固定少量在线玩家，不做交互，逐档增加离线存量。记录完整重绑次数、扫描数量、CPU、分配及 tick 时间；这直接验证 WP-A，不把空闲服务器偷换成空世界。

**活动实验：**固定离线量，增加 ACTIVE 任务和逻辑用户；交错提交、背包变化、击杀、区域、条件和结算。所有预期结果由测试台账计算，不只看最后无异常。

**组合实验：**选择已能承载的中高档，在持续推进时叠加换维度、退出重连、正常存盘和无内容 reload。随后做一个真实资源变更／包状态更替样例，核对缓存失效与受影响实例边界。

规模生成和传送引起的新区块生成开销单列。使用预生成小测试区域完成主比较，再单独观察冷区块场景，避免把 Minecraft 地形生成全部归因于 DGR。

### 8.3 运行时长与重复

- 性能比较：每个主场景预热约 5 分钟、测量至少 10 分钟；基线与候选各做 3 次，次序交替。短确定性断言不需要机械等待。
- 持续运行：最终候选至少一轮 **60 分钟**混合负载，中途登录／登出、区域切换、任务推进、媒体打开关闭与存盘。资源充足可加 120 分钟高档，不能替代 60 分钟核心样例。
- 冷恢复：持续运行后正常停服、重新启动，复验同一批身份／任务／收据；客户端冷启动重新连接。只有进程还活着，没有结果断言，不算通过。
- 同 JVM 世界切换专门运行；每次都新开 JVM 会掩盖静态缓存／队列残留，不可替代。

本版不要求建设长期无人值守压测服务。由 Codex 在当前执行环境管理脚本、进程和输出，无法完成时如实标明未运行，不承诺离线后台继续测试。

## 9. 核心场景矩阵（执行与探索共同使用）

| ID | 场景 | 必须观察／断言 |
|---|---|---|
| ST01 | 无玩家、无故事；有存量但无在线玩家 | 空闲开销合理，不无故加载／重绑、写脏、发包或启动剧情 |
| ST02 | 有在线静止玩家＋大离线存量 | 完整重绑次数与轮询解耦；数据不丢；低负载持续可响应 |
| ST03 | 大量 ACTIVE Task 混合目标 | 实际 tick／事件推进，计数锁存、前置、dormant、并行及结算正确 |
| ST04 | 两名实际联网玩家跑相同 Story | A 操作不改 B 游标、背包、奖励、Choice 可选态；广播不串 transport |
| ST05 | 多玩家跑不同 Story／组成员 | 状态独立；共享只读资源可复用；一个故事失败不改变无关实例 |
| ST06 | 同一 NPC／同一提交点并发到达 | 服务端串行判定每位玩家有效请求；不足量不扣、重复点击不重奖 |
| ST07 | 合法 pending A→B、重复恢复、目标已存在 | 经生产登录／周期入口恢复，null-first 不再断路，claim／run 幂等 |
| ST08 | 深 Flow、跨 Story 环、复杂 Logic | 受控预算与错误；普通 tick／队列继续；失败不是 JVM 栈溢出兜底 |
| ST09 | 台词／Choice／Task／Title 中跨维度 | 同世界进度保留；位置请求重新核验；不重复奖励，不使用旧实体引用 |
| ST10 | 同客户端先世界 A 后 B，再回 A | 故意用相同 Story UID、媒体 ref、维度号和玩家 UUID；B 不继承 A 状态，A 回来可正确恢复 |
| ST11 | 断连 X→连 Y，旧异步响应晚到 | 旧控制帧／下载完成／UI 回调不污染新连接；资源释放；不能按相同 serverIP／文件名简单放行 |
| ST12 | 死亡、重生、区块卸载重载、NPC 消失 | 输入可退出，当前宿主重新核验；不指向已死亡玩家实体，不重复扣物／结算 |
| ST13 | 无内容 reload、真实资源更新 | 未变状态不重置；变化后缓存准确失效；没有“修复完永远不刷新” |
| ST14 | Enabled／Disabled、Error／Conflict、卸载 | Disabled 新旧实例语义不变；不能借重绑误删无关进度；无失效包继续发奖 |
| ST15 | 正常 UI 导出包完整库存与零结算 | 同字节作者包经真实角色交互、一次奖励、重连／重启；零结算不自动完成 |
| ST16 | 队列短突发、持续流量、单任务异常／慢任务 | 预算可见、无饥饿、无静默丢业务；异常回传；单慢任务被定位，不能宣称队列能抢占 |
| ST17 | 多人首次媒体、客户端大图与多层切换 | 后台 IO 与上传预算有效；未就绪不阻断剧情；记录帧时间／显存可用指标／堆和在途量 |
| ST18 | 全部缓存名额受保护、取消与资源共享 | 仍守 3／10 bundle 规则，后续媒体排队；剧情可继续；共享引用不被误删 |
| ST19 | 下载／解码／提交排队中退出／换世界／停服 | 每个 in-flight／lease／pending 最终释放或被正确继承；迟到结果不复活旧世界 |
| ST20 | 连接抖动与应用层延迟／过期请求 | 使用隔离驱动延迟或重复合法消息，不谎称 TCP 丢包；过期请求安全拒绝，UI 不永久等待 |
| ST21 | Live Bridge／诊断／包 GUI 在状态变化或不可用时 | 直接请求边界有回应、正确 request id、不假装无进度；无崩服／卡住／无限日志 |
| ST22 | 60 分钟混合运行后保存冷恢复 | 无累积队列／句柄／世界引用泄漏，游标、库存、收据、运行状态与台账一致 |
| ST23 | 正式 CNPC 环境正常代表链 | 个体／组、转移、解绑、实体交互＋任务推进；不得以原版实体替代此项 |
| ST24 | 固定种子探索序列与最小反例 | 多时点组合、状态不变量逐步检查；失败有 seed、事件日志、最小复现和最终回归 |

## 10. 主动探索未知 Bug：不能只照已知复现跑一遍

### 10.1 可重放状态序列

建立一个小的测试状态机／场景生成器，只驱动现行业务，不成为生产引擎。默认 **5 个固定 seed，各至少 2000 次逻辑操作**；实际网络／GUI 使用较短可观察序列，另标层级和数量。

候选操作：开始故事、推进台词、选择可用选项、提交／不足量提交、背包增减、杀目标、区域进入离开、条件翻转、重复请求、保存、reload、包禁用／启用、登出／登录、死亡换实体、世界切换以及延迟回调交付。只在能定义预期的状态上生成合法／明确非法操作。

每一步检查小而独立的预期台账：有效操作是否完成、拒绝是否无副作用、玩家／world 归属、库存和奖励守恒、是否额外启动 run、是否丢失 pending。不能拿被测 Runtime 自己输出的状态作为唯一“正确答案”。

增加三个易暴露时序问题的交错：提交前后断线、资源更新前后到达旧回调、世界退出后完成媒体 IO。Forge 世界修改仍在主线程，不为了制造“并发”在测试中非法多线程调用实体 API。

### 10.2 每个新发现的闭环

```text
发现异常
→ 保存程序／包／世界样例 hash、seed、步骤、线程栈和指标窗口
→ 用更少玩家／节点／操作缩小到最小复现
→ 确认属于 DGR、测试驱动、第三方或测试机资源瓶颈
→ 在本版范围内定点修复
→ 加入永不依赖人工记忆的回归测试
→ 使用最终候选重跑原失败场景及相关普通场景
```

测试驱动失败不能算产品失败；同样不能通过删除失败场景、换一个容易的 seed 或大幅降低任务量来冒充修复。需要调整负载必须保留原失败档及原因。

遇到大范围问题时先分级：崩溃／主线程失去响应、跨用户／跨世界写错、重复奖励或丢事务优先；可复现明显延迟和内存增长其次；仅表现细节另列。不能只修容易的 UI 问题，把高影响失败留在“以后”。

对确认属于本版稳定性的 Bug，Codex 可自主修补后复验；会改变产品语义或越过 §1.3 的，暂停该项说明，不擅自扩大工程。

## 11. 必须记录的指标与判定门槛

### 11.1 不是只看 FPS 或最终无报错

| 维度 | 最少指标 |
|---|---|
| 服务端 | 完整 tick 执行时间的 p50／p95／p99／max、超过 50／100／250 ms 的次数、实际 tick 数／墙钟时长、DGR 热路径耗时与次数 |
| 调度 | 当前／峰值排队数、最老任务等待、接收／完成／合并／拒绝／取消数、各类延迟、在途占用是否回落 |
| 内存与线程 | 堆占用、GC 次数／暂停、线程和打开句柄可用指标、旧世界／连接存活、资源计数；不能只看强制 GC 后的瞬时值 |
| 交互 | 同机可比链路中的点击／请求发出→正确响应 p50／p95／p99／max；客户端、服务器两个时钟不直接相减 |
| 客户端 | 相同位置和设置的帧时间分位／尖峰、平均 FPS 辅助、媒体解码／上传时间、纹理数／像素预算和失败恢复 |
| 正确性 | 已开始／完成／取消实例、库存、XP／奖励收据、pending／run／transport、身份归属与测试台账是否一致 |

tick 测量须包含 DGR 所在事件阶段；不能只包住一个 END 处理器，就把它的耗时称作完整服务器 MSPT。无法包住完整 tick 时标记为 DGR 子段指标，另取可靠完整 tick 数据。

只用平均值会掩盖长停顿。百分位样本数和时长一起记录，基线／候选使用同样算法和采样方式。采样输出有界，禁用逐事件大量写盘以免测量器制造卡顿。

### 11.2 默认工程门槛

以 20 tick/s 作为测试目标，每 tick 的总时间预算为 50 ms；这只是计算目标，不是已经测得的性能。P0 在未修改候选前冻结“常规参考档”和“压力探索档”。建议常规档选能让基线世界本身正常运行的负载，默认从 4—16 个逻辑用户、100—1000 个 ACTIVE Task 中确定，**实际 N 玩家数另列**。

| 类别 | 门槛／处理 |
|---|---|
| 所有正常必测场景 | 零 DGR 引发的崩溃、未捕获主线程异常、跨世界／跨玩家串写、重复 DGR 奖励或永久卡死；单项触发即失败，不用性能均值抵消 |
| 重绑结构 | 同世界／同快照初始化完成后，稳定轮询的完整重绑次数为零；真正失效后必要重绑有限且状态正确 |
| 常规参考档 | 默认目标完整 tick p95 ≤40 ms、p99 ≤50 ms；所有 ≥250 ms 停顿定位，任何可重复的 DGR 同步热点导致 ≥500 ms 停顿为阻塞问题 |
| 优化对照 | 相同输入下 WP-A 完整恢复／编码次数显著消除，记录实际耗时与分配差异；不虚构必须提升 N 倍 |
| 正常交互 | 无主动等待／网络限速的本地参考链，默认 p95 ≤250 ms、p99 ≤1000 ms；Choice／条件的作者等待和媒体首次下载单列，不污染统计 |
| 队列 | 在已声明的持续负载内不无限增长；停止突发后默认 5 秒内回到接近空闲；有意 10 秒 IO 延迟须另列设计等待，不伪报队列死锁 |
| 长时与生命周期 | 退出后业务队列／在途操作终结，无持续线性增长的旧世界／连接引用；合法 warm cache 在已有边界内可保留，不要求一切清零 |
| 客户端代表场景 | 同硬件同画面比较；首次上传单列；DGR 热状态不产生可重复的长冻结；≥250 ms 帧尖峰定位，≥500 ms 的可重复 DGR 同步阻塞作为本版失败 |

如果测试机本身在无 DGR 工作的对照就达不到门槛，记录环境瓶颈，换较低参考档并保留原档，不把无法判断写成 PASS。选定档位及调整原因必须公开。压力档超过容量拐点后可以记录性能失败，但不能以删任务、丢交易或跨用户错写来降级。

不对公网延迟、任意硬件、任意整合包或最大人数给绝对保证。最终结论写成“在环境 E、实际网络玩家 P、ACTIVE Task T、图规模 G、事件率 R、时长 D 下的结果”。

### 11.3 安全停止条件

默认隔离监测器在服务器连续约 10 秒无 tick 心跳、反复超长 tick、内存接近安全余量、无界日志或队列持续上涨时先停新负载并抓取连续线程栈、进程状态、指标窗口；优先正常停服。仍失去响应时只定向处理本次可丢弃进程，保留现场。

不得为了让测试继续而把 watchdog 永久关闭、无条件延长所有超时、增加超大堆、删世界状态或捕获 `Error` 后打印 PASS。启动／区块生成等长阶段按实际阶段标注，不与稳定负载阶段混算。
