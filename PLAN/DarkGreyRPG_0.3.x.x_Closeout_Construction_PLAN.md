必须覆盖下面这些边界，并定位到对应当前源码或最终合同；不引用旧草案当成现行规则。[S12]

## 4. WP-B：解除构建对开发机目录的强绑定

### 4.1 保留工具链，只改变发现和配置方式

本轮不升级现有 Java、Gradle、.NET 或插件版本来“现代化”。先分别记录：**Gradle 启动 JDK、编译目标／工具链、Minecraft 实际运行 Java、Studio SDK**。README 的“Java 8”与仓库中 Gradle 启动路径不能混成一个结论。[S04][S05]

从已提交的 `gradle.properties` 移除私人绝对 JDK 路径，保留构建所需版本和公共配置。个人路径移到用户本地配置或明确环境参数，不提交个人设置。处理后同时验证作者原开发环境仍可通过显式配置工作。

### 4.2 dotnet 与发布脚本

`studio/package-studio.ps1` 保留现有职责和目录布局，最小增加工具位置的参数／环境覆盖，并可从 PATH 定位 dotnet。建议顺序：**显式参数 → 项目约定环境变量 → PATH**。找到后先验证 SDK 版本与所需能力，给出明确缺失信息；不能扫描全盘或静默安装到系统目录。[S06]

不得仅移除 `$dotnetPath`：脚本还根据 SDK 查找 HostModel、apphost 模板及运行库声明，必须沿实际选中的 SDK 根继续解析。不要把另一个 SDK 目录下的许可或宿主模板混进候选程序。

支持含空格、中文和非 E 盘的源码／输出路径。`.tooling` 等临时目录保持相对当前工作副本；`-OutputDirectory` 继续有效。不得为“通用化”改变根 EXE＋Program／Tools／Docs／Data 布局或破坏 Data 白名单保护。

### 4.3 FFmpeg 与本地依赖要有可执行的准备入口

把工程里 FFmpeg 的本地路径提取为可覆盖的构建属性或统一准备目录；默认路径可以仍在仓库 `.tooling`，但必须有清楚、可复现的准备方式。[S07]

采用一个轻量准备脚本或明确命令，不新建依赖平台：锁定实际批准的版本、来源和校验值；用户可提供已有合法副本。需要下载时必须来自核实的上游／分发来源，并保留对应许可证材料。不能用无版本 `latest` 代替锁定，也不能把可执行文件在每次应用启动时自动下载。

下载／准备先到临时文件，校验成功后再置入正式工具目录；错误、取消或断网不能覆盖已有有效工具。重复运行不重复下载已验证文件，离线已有工具可以复用；全新离线机器缺依赖时明确失败，不假装构建成功。

CustomNPC+、UniMixins、JLayer 的源码依赖获取方式随 WP-C 的事实结论同步。若某个本地修订 JAR 没有可验证来源，不用随意找到的同名新版顶替；将准确来源缺口单独记录。

### 4.4 不削弱构建和测试来换取绿色

保留检查、格式校验和真实测试入口；不关闭校验、不删失败断言、不把所有异常吞掉。Java 有独立的 `JavaExec` Probe，**`build` 成功不等于全部 Probe 已执行**。[S13]

### 5.1 CustomNPC+ 必需还是可选：用运行链证明

检查入口类、静态类型引用、注册、反射适配、测试 classpath、JAR 元数据与最终成品内容，找出不一致来自注释过时，还是实际运行存在隐藏硬依赖。[S08][S09]

在隔离环境执行两组最小验证：

| 环境 | 验证重点 |
|---|---|
| 基础组：Minecraft／Forge＋DGR及经核实真正必需的依赖，不含 CustomNPC+ 及仅为其存在的依赖 | 客户端进世界、专服启动并连接、原版实体绑定、Story→Session→Task 基础链。 |
| 集成组：加入当前使用的准确 CustomNPC+ 构建及其确需依赖 | 启动、实体识别／绑定、实际交互一次、任务／会话正常进入。 |

不能只看主菜单能否出现；也不能因为测试故事恰好使用 CNPC 专属实体，就断言 DGR 框架整体必需 CNPC。

结论必须三处一致：**README／新手说明、Gradle 依赖注释、实际模组元数据和加载行为**。若基础组通过，清楚写“基础功能不依赖 CNPC，集成功能需要”；若确有硬依赖，列出具体证据和最小准确安装要求，不凭旧文档强行承诺 Optional。明显遗漏可定点修复；大规模解耦不在本轮默认范围。

### 5.2 区分四件不同的事

**DGR 自身的代码许可、第三方源码／二进制许可、开发时依赖、正式成品实际随附内容**分别核对。不要把“没有打进 DGR JAR”说成“没有任何再分发”：仓库若跟踪该二进制，本身也是本轮需要说明的分发位置。

建立紧凑清单，覆盖实际存在并用于本次构建／分发的组件：CustomNPC+、UniMixins、JLayer、随附 FFmpeg／FFprobe、.NET／WPF 运行库，以及代码、素材和工具中发现的其他实际第三方内容。每项写明：

`名称／准确版本或来源修订／SHA-256／用途／仅开发或随附位置／许可原文来源／需要随附的材料／核对状态`。

来源只采用对应版本上游、原始发行包或权利人的明确说明。没有查到就写“未确认”，不根据文件名、项目名或最新版网页推断旧二进制许可。

FFmpeg 的许可会受其实际构建配置影响；因此核查随附副本的版本与构建信息，而不是只写“FFmpeg＝LGPL”。原文中的库链接说明也不能未经判断直接套到独立命令行程序的使用方式上。[E02] 不在本 PLAN 预判某个具体第三方组合已完全合规。

### 5.3 DGR 自身许可证：不得让 Codex 替作者作主

先搜索当前仓库、现有发布说明、源文件声明及用户已经给出的许可决定；已有明确合法范围则保持并整理。**本次对话没有指定 MIT、Apache、GPL 或其他项目许可证。**

没有既有决定时，Codex 完成来源盘点、第三方材料和一段面向用户的简短决策说明；只将“DGR 自身要采用哪种授权方式”集中提交用户确认，其他工程工作继续。不得先放入一个默认 MIT LICENSE、擅自承诺商业使用／再分发，也不得自行编一份“禁止商用”的开源许可证。

公开仓库和明确的开源授权不是同一个概念；GitHub 官方也将许可证选择列为作者需要知情决定的事项。[E01] 用户可决定是否开放以及如何授权，不因“正式内测”就强迫其采用某种开源策略。

未确认时状态为 `PROJECT_LICENSE_PENDING_OWNER`。它表示相关对外授权声明尚不能完成，不等于技术构建、主题修复或隔离测试都要停工，也不等于可以把公开再分发准备状态标为通过。

### 5.4 补齐材料，不做历史清仓

按核实结果补充根 `THIRD_PARTY_NOTICES.md` 及需要保留的原始许可文本，并将必要材料纳入现有 Studio／Runtime 打包白名单。不要覆盖或删掉已有有效版权声明，不用统一改头替换第三方原文。[S03]

某个依赖的公开分发依据不明时，明确限定受影响的组件及发布项；优先补准确材料或改为明确的本地获取方式。**不以许可检查为借口删除整个 libs、清理所有测试证据或重写 Git 历史。**若历史分发确需处理，先单独说明，不擅自执行不可逆操作。

## 6. WP-D：Studio 主题菜单定位与修复

### 6.1 已知现象与排查链

0337记录是“指定 Light 启动正常，菜单切换当次未生效”，并未证实全部用户都必现。[S10] 先在当前权威程序和相同源码候选各复现一次，区分真实菜单缺陷、旧程序映像、测试调用未命中以及设置恢复等可能原因。

定位范围：`MainWindow.xaml`／`.xaml.cs` 的菜单和绑定 → `ThemeSettingsViewModel` 的命令与 `SelectedTheme` → `App.ApplyTheme` → 主题资源更新 → `SettingsService` 读写。[S14] 记录点击是否触发命令、主题枚举是否变、画面是否变、本副本设置是否落盘，不能仅凭截图颜色猜根因。

### 6.2 期望结果

- 保留现有 System／Light／Dark 三个选项，不新增主题管理系统；新副本仍默认 Dark，旧副本尊重已保存选择。
- 用户实际点击菜单后，当前窗口及已打开的资源／节点／Inspect按预期更新，不要求重启才能生效。
- 主题更新不关闭项目、不重新读取项目图、不清空未保存文字、选择、折叠状态和撤销历史。
- 退出重开仍为最后成功保存的主题；System 的语义与现有框架一致，不能被错误写成一次性取色。
- 每份便携 Studio 只读写自己的 Data；不回退到共享用户目录，也不改变系统注册表或Windows主题来让测试通过。
- 设置写入失败时给出明确反馈，不能虚报“已保存”；程序和项目仍安全。

若无法复现，保留准确环境、版本、实际点击及状态读回；修正错误的测试方法而不是随便改代码。未定位不得填写 `FIXED`；必须说明“本轮未复现／原记录原因已证实”各自的证据。

### 6.3 验证方式

新增或补足 `ThemeSettingsViewModelTests`、设置服务和菜单绑定相关回归；另用真实菜单操作 Dark→Light→Dark→System，覆盖未打开项目和打开含未保存编辑的项目两种状态。再验证重启恢复、两个隔离副本各自保存、主题切换后的正文／帮助／占位文字可读性。

自动调用 ViewModel 只能证明逻辑层，直接修改配置后重启只能证明启动读取，**两者都不能代替“菜单点击生效”这一验收点**。

## 7. WP-E：干净环境构建与最小真实闭环

### 7.1 干净的定义

使用另一份源码副本和独立输出／依赖缓存，不复制原开发目录的 bin、obj、dist、项目 Data 或完整 `.tooling` 来蒙混。优先使用新 Windows 用户／VM；也可使用明确隔离路径，**但报告里必须说明隔离级别，不能把同机另一个目录称为全新系统**。

源码必须包含本轮修改。能在授权范围内生成准确提交时记录提交；否则在基线的干净副本应用本轮 patch，并记录 patch SHA-256与新增文件清单。不得只重建原0337提交却宣称验证了扫尾修复。

测试使用非作者固定目录；至少包含一个带空格或中文的路径。依赖从文档所列入口准备，不依赖开发机隐藏资源。首次联网恢复与之后已有缓存离线执行分开记录，不承诺全新离线机器可以无中生有完成构建。

### 7.2 两条路径分别证明

**源码路径：**按 `docs/BUILDING.md` 从依赖准备开始，完成 Runtime 构建／必要 Probe、Studio Core／WPF 相关测试和完整 Windows x64 自包含目录输出。记录工具实际路径与版本、命令、退出码、依赖来源和产物哈希。

**使用路径：**在没有源码目录依赖的隔离可写位置运行候选完整 Studio 目录；证明运行库来自 Program，媒体工具来自 Tools，首次状态来自本副本 Data。没有 .NET SDK／全局运行时的环境最有说服力；只能隔离 PATH／DOTNET_ROOT 并读取加载模块时，准确说明证明范围，不把“机器本来有运行时”隐藏掉。[S03]

本轮不需要创建新的对外成品 ZIP。可验证隔离完整候选目录；已有获准发布的 ZIP 若用于安装基线验证，必须标明是旧发布资产，不能把它当成新源码产物。之后用户授权发布时，再按 release skill 生成新成品。

### 7.3 真实闭环，使用最小测试内容

复用或制作一个很小的当前格式测试项目：一个独立 Story，以及一个含两个成员、具有一条实际 Flow或Logic关联的 Group。包含一段可选择会话、一个简单任务、一次固定奖励和一张图片／一段有明确使用权的音频即可；不建立大型示例游戏。

通过实际 Studio 打开、编辑、保存并导出 `.dgrs`／`.dgrs.g`，把**同一批导出字节**放到隔离游戏端的 `DarkGreyRPG/StoryPackages`。不要拿手写 JSON 替代要验证的正式导出物。[S03]

以本轮正式 Runtime JAR 启动隔离专服并用匹配客户端连接：确认版本、加载包、触发故事、进入会话、推进任务、完成结算、取得一次奖励。测试内容要能明确产生结果，避免把故意零结算的 Task 当作运行卡死。

随后在该隔离环境做一次不改变包内容的 `/dgr reload`、一次断开重连和一次正常保存／停服／重启。检查任务／故事结果、完成记录和奖励未重复；测试只证明这一小条链路，不延伸为长时可靠性保证。再做一次集成服务器的简短启动／加载／交互检查。

O 管理器的普通 OP 打开／关闭及非 OP 拒绝做基础回归即可；**不纳入 JourneyMap 默认键冲突**。测试环境不加小地图来制造本轮已排除的问题。

媒体只验证实际导入／显示／播放的基本路径，不运行长期纹理、缓存、租约压测。声音需要实际听到才能写听音通过；只有调用或下载日志时准确注明。

### 7.4 数据安全与更新说明

更新开发者权威 dist 前后，核对 Data 的文件清单、大小与哈希；部署过程不得改写个人 Data。程序实际启动后正常产生的日志／偏好变化，与部署写入分别记录，不能把必要新增日志说成数据损坏。

验证默认 Data/Projects 和明确选择的外部项目位置，移动完整便携程序目录后内部项目仍可恢复，外部项目不被自动搬回。只用隔离测试数据，不触碰用户真实项目来证明功能。

给服主写一小段具体的更新／回退说明：正常停服、备份世界与 DGR配置／故事包、保存确切 JAR版本，更新失败恢复匹配的一组备份。说明需要备份的实际路径；不做自动更新器，不要求用户理解 SavedData内部结构。
