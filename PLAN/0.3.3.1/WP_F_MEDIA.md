# WP-F media streaming implementation note

This bounded implementation changes the Java DGRS package path to retain entry metadata and structural JSON only. `DgrsArchiveReader` scans each ZIP entry with a 32 KiB buffer, enforces the existing entry/count/aggregate limits, and consumes the complete entry so ZIP CRC errors are rejected. `readBytes` remains a compatibility API for structural callers; it re-opens one bounded entry and is never used for declared media during a DGRS snapshot.

`StoryPackageSnapshotReader` now excludes `required_resources.media` from its byte map. `StoryPackageMediaValidation` derives reachability from structural JSON and validates each media entry through an incremental SHA-256 and stream container parser. PNG chunk CRC, IHDR dimensions, IDAT and IEND are preserved; OGG page CRC, Vorbis identification and EOS are preserved; JPEG keeps the existing SOI/EOI guard.

Accepted archives are copied to `.dgrs-runtime/generations/<content-fingerprint>.dgrs` through a bounded `.part` copy and atomic publication. A loaded package reads only that immutable generation. The first legal request for a media reference materialises a fingerprint-keyed file under `.dgrs-runtime/media` through one synchronised `.part` operation, verifies size, SHA-256 and container structure, and then serves 32 KiB random-access chunks. Generation owner leases and request leases keep an active source alive across reload and transfer; retired generations are removed only after the final lease. Startup recovery removes only safe, controlled `.part` files.

The focused probes are `darkgrey.rpg.project.packages.DgrsMediaStreaming0331Probe` and `darkgrey.rpg.project.packages.DgrsMediaLifecycle0331Probe`. The lifecycle probe covers cache deletion/rebuild, eight concurrent requests converging on one path with no `.part` residue, invalid format/path/hash and corrupt-container rejection, generation lease-safe retirement, startup `.part` recovery, controlled-root reparse guard, cache disk bytes, open-handle reporting, and a retained/peak heap comparison for 8 MiB versus 32 MiB same-entry archives. The measured run retained 4,472 bytes for the small reader and added 1,008 bytes for the large reader; scan peak deltas were 198,864 and 65,568 bytes. The evidence is `PLAN/0.3.3.1/evidence/media/media-lifecycle-0331.txt`.

`CanonicalMediaServer` authorises and selects a package on the server thread, pins its generation, and queues bounded media work on a two-thread/64-entry worker. The worker schedules the final send back to the server scheduler and releases its generation lease; the final send rechecks current presentation ownership. The repository `compileJava` and `testClasses` tasks pass with `JAVA_HOME=E:/Java/jdk-25.0.1` and `GRADLE_USER_HOME=.gradle-user-home`; both focused probes pass when launched with an E-drive probe root.

Remaining risks: retention budgets and client playback policy remain outside WP-F. The media worker is intentionally bounded but still uses the existing server scheduler for final sends, so a stalled server tick can delay delivery while preserving authorization and bounded chunk memory. Reparse-point creation was unavailable on the verification machine and the operating-system open-handle MXBean returned `-1`; these gates need a Windows environment that exposes both facilities. Full Minecraft tick/runtime/client acceptance remains outside these probes.
