# DarkGrey_RPG 0.3.0.0 设计与开发计划

> **版本定位**：测试阶段的第三个里程碑版本。
> **核心意义**：彻底明确 DarkGrey_RPG Studio 的主工作流、Story / 会话 / 任务三层节点架构、流程与逻辑两类接口，以及资源树驱动的创作方式。
> **当前基线**：DarkGrey RPG Studio 2.1.3，Java Runtime 0.5.0。
> **目标版本**：DarkGrey_RPG 0.3.0.0。
> **计划状态**：架构结论已锁定；Stage 0–6 已实施并通过阶段 Gate；Stage 7 本地发布验收已完成。2026-08-29 17:01 +08:00 用户已授权 GitHub 提交与推送，tag、merge 和 GitHub Release 仍未授权。
> **重要说明**：本计划优先级高于仓库中旧的 2.1.x UI 规划和旧 Story / Dialogue / Quest 编辑器设计。实施过程中不得重新引入已明确否决的“入口 / 返回 / 并发节点 / Task 内嵌会话”等方案。

---

# 1. 新版本号规则

DarkGrey_RPG 从 0.3.0.0 开始采用四段式版本号：

```text
稳定阶段.里程碑版本.功能更新.补丁更新
```

## 第一段：稳定阶段

```text
0 = 测试版，尚未正式投入生产使用
1 = 正式版
```

当前仍然是测试阶段，因此为 `0`。

## 第二段：里程碑版本

用于标记架构、产品流程或核心能力发生重大变化的版本。

```text
0.3.0.0
  ↑
  3 = 第三个重大里程碑
```

0.3.0.0 的里程碑意义是：

- Story Flow 被提升为 Studio 的主要工作台；
- 角色、会话、任务转为资源树；
- 会话和任务拥有局部节点图；
- 正式区分 `● 流程接口` 与 `◆ 逻辑接口`；
- Task 从传统任务表单改为纯逻辑聚合资源；
- Studio 的核心创作语言得到统一。

## 第三段：功能更新

同一里程碑架构内的普通功能版本。

示例：

```text
0.3.1.0
0.3.2.0
```

## 第四段：补丁更新

轻量修复、小型交互调整和补丁。

示例：

```text
0.3.1.1
0.3.1.2
```

## 版本统一要求

0.3.0.0 开始，Studio 与 Runtime 的对外版本统一显示为：

```text
DarkGrey_RPG 0.3.0.0
```

数据 Schema 版本继续独立维护，不得把产品版本直接当作 JSON Schema 版本。

# 2. 0.3.0.0 的产品定位

DarkGrey_RPG 0.3.0.0 不再将 Studio 理解为：

```text
先分别填写角色、对话、任务
→ 最后进入 Flow 做简单连线
```

新的工作方式是：

```text
Story Flow 是最主要、最常驻的剧情工作台

角色、会话、任务
= 左侧资源库中的可复用资源

Inspector
= 右侧当前节点 / 当前资源的属性编辑器
```

创作者的大部分时间应当停留在节点工作台中，通过资源树、拖拽、局部图和 Inspector 完成剧情编排。

# 3. 已锁定的核心架构原则

## 3.1 Story Flow 是剧情宏观编排的唯一来源

Story Flow 负责：

- 剧情何时开始；
- 调用哪一个会话；
- 激活哪一个任务；
- 查询哪些逻辑状态；
- 执行奖励和动作；
- 进入其它剧情；
- 何时终止当前剧情。

Project Story Graph 继续保持：

```text
由 Story Flow 中的跨 Story 关系派生
逻辑只读
不是第二套逻辑来源
```

## 3.2 每一个作用域只有一份内部逻辑来源

```text
Story Flow
→ 当前 Story 的宏观流程与逻辑

会话局部图
→ 当前会话内部的台词、选择和局部逻辑

任务局部图
→ 当前任务的目标状态与纯逻辑组合
```

三者共享同一个 Graph Editor 技术体系，但节点集合和运行语义不同。

## 3.3 会话、任务在 Story Flow 中都是高度聚合节点

本文中的：

```text
【会话】
【任务】
```

专指 Story Flow 中代表完整资源的聚合大节点。

它们不是会话内部的台词节点，也不是任务内部的目标节点。

## 3.4 Task 内部禁止嵌套会话

任务内部只描述：

- 目标；
- 目标激活关系；
- 目标完成状态；
- 与 / 或 / 非；
- 对外逻辑状态；
- 最终结算结果。

任务内部不得放入：

- 【会话】节点；
- 【台词】节点；
- 【选择】节点；
- 奖励动作；
- 进入其它 Story；
- Story 级剧情表现。

会话、任务和奖励的顺序必须由 Story Flow 编排。

## 3.5 Actor 继续保持叙事身份边界

Actor 负责：

- 项目级角色 ID；
- 显示名称；
- 标签；
- 备注；
- 叙事身份；
- 与 CustomNPC+ 实体的绑定身份。

以下内容继续由 NPC / CustomNPC+ 负责：

- 血量；
- 皮肤；
- 模型；
- 战斗；
- 移动；
- AI；
- 动画。

0.3.0.0 不把 DarkGrey_RPG 扩张为 NPC 属性编辑器。

## 3.6 同一玩家、同一 Story ID 同时最多一个实例

固定规则：

```text
player + story_id
→ 最多一个 Active StoryInstance
```

玩家可以同时参与不同 Story，但不能同时运行同一个 Story 的两个副本。

当 Story 已处于运行中：

- 【开始】上的所有启动钩子不再创建新实例；
- 不重启 Story；
- 不清空当前进度。

上一轮 Story 结束以后，是否允许开始下一轮，由重复策略决定。

# 4. 统一术语

## 4.1 Story Flow

### 【开始】

Story Flow 唯一的最初节点。

- 是特殊触发器；
- 无 `● 流程输入`；
- 内置所有已支持的 Story 启动钩子；
- 每增加一个触发配置，就增加一个具名 `● 流程输出`；
- 至少有一个触发配置；
- 不允许删除。

初始触发类型至少包括：

- 进入剧情；
- 角色交互；
- 进入区域。

### 【终止】

Story Flow 的最终节点。

- 只有 `● 流程输入`；
- 无流程输出；
- 进入后当前 StoryInstance 完全终止；
- 当前 Story 内仍活动的任务、等待、状态更新和临时机制全部停止；
- 可以存在多个【终止】节点，但它们都表示 Story 终止。

## 4.2 【会话】内部

### 【起始】

会话局部图唯一的最初节点。

- 不包含触发钩子；
- 一个 `● 流程输出`；
- 一个 `◆ 逻辑输出`；
- 不允许删除。

外部聚合【会话】节点可以提供一个可选 `◆ 逻辑输入`。该值进入局部图后，由【起始】的 `◆ 逻辑输出`提供给会话内部逻辑使用。

### 【台词】

NPC 说话节点。

`【台词】`只表示 NPC 或角色说的话。

### 【选择】

玩家说话 / 玩家选择节点。

`【选择】`只表示玩家可选的回答。

### 【结束】

会话局部图的终点。

- 一个 `● 流程输入`；
- 无内部流程输出；
- 可以有多个；
- 每个【结束】拥有自定义名称；
- 每个【结束】映射为外部聚合【会话】节点的一个具名 `● 流程输出`。

### 【逻辑输出】

会话局部图向父级公开逻辑状态的边界节点。

- 一个 `◆ 逻辑输入`；
- 无内部逻辑输出；
- 可以有多个；
- 每个节点映射为外部聚合【会话】节点的一个具名 `◆ 逻辑输出`。

用途包括：

- 玩家选择了某个选项；
- 会话内部某个条件成立；
- 会话达到某种进度；
- 会话内部组合逻辑结果。

## 4.3 【任务】内部

### 【激活】

任务局部图唯一的最初节点。

- 固定唯一；
- 不允许删除；
- 只有一个 `◆ 逻辑输出`；
- 外部 Story Flow 的 `●` 信号进入聚合【任务】节点后，TaskInstance 进入 Active，【激活】输出 true；
- Task 未激活时，【激活】输出 false。

### 【目标】

任务内部承担具体任务内容的节点。

例如：

- 击杀 10 个史莱姆；
- 收集 10 个铁锭；
- 与酒馆老板交互；
- 进入某个区域。

一个【目标】至少具有：

```text
◆ 启用输入
◆ 状态输出
```

语义：

- 启用输入第一次变为 true 时，目标开始工作；
- 目标激活后持续记录自己的进度；
- 达到目标后，状态输出变为 true；
- 同一个 TaskInstance 中，目标不会因上游重新求值而自动清零；
- Task 结算或 Story 终止时，目标停止工作。

### 【与】

纯逻辑节点。

```text
N 个 ◆ 输入
1 个 ◆ 输出
```

所有输入为 true 时输出 true。

### 【或】

纯逻辑节点。

```text
N 个 ◆ 输入
1 个 ◆ 输出
```

任意输入为 true 时输出 true。

### 【非】

纯逻辑节点。

```text
1 个 ◆ 输入
1 个 ◆ 输出
```

输出输入值的逻辑反值。

### 【逻辑输出】

任务内部向外公开状态。

- 一个 `◆ 逻辑输入`；
- 无内部输出；
- 可以有多个；
- 映射为外部聚合【任务】节点的具名 `◆ 逻辑输出`；
- 不结束任务；
- 不推动 Story Flow。

### 【结算】

任务局部图唯一的最终节点。

- 固定唯一；
- 不允许删除；
- 用户可以增加、删除、命名、排序多个 `◆ 逻辑输入槽`；
- 输入槽从上到下判定；
- 越上方优先级越高；
- 第一个为 true 的槽成为唯一 Task Result；
- 对应生成外部聚合【任务】节点的一个具名 `● 流程输出`；
- Task 随即停止运行；
- 若全部输入为 false，Task 保持 Active。

# 5. 两种接口

## 5.1 ● 流程接口

`●` 表示执行路线。

规则：

```text
流程输出：
同一个输出端最多连接一个输入端

流程输入：
可以接受多个流程输出来源
```

口诀：

> **● 流程：去向唯一，来源可多。**

原因：

- 一个流程输出如果同时连向多个目标，会产生“执行哪条 / 是否都执行”的歧义；
- 多个前驱汇入同一个流程输入没有歧义，任意前驱到达都可以执行该节点；
- 0.3.0.0 不引入隐式并发，也不提供“并发 / 并行分发”节点。

## 5.2 ◆ 逻辑接口

`◆` 表示状态、布尔关系和逻辑引用。

规则：

```text
逻辑输出：
可以连接多个逻辑输入

逻辑输入：
最多接受一个逻辑来源
```

口诀：

> **◆ 逻辑：来源唯一，去向可多。**

原因：

- 一个状态可以同时被多个地方读取；
- 一个逻辑输入若接受多个来源，就会产生隐藏的 AND / OR 语义；
- 多条件组合必须通过显式【与】【或】【非】节点表达；
- Studio 不得在一个逻辑输入上偷偷执行默认 AND 或默认 OR。

## 5.3 流程与逻辑不能混接

禁止：

- `● → ◆`
- `◆ → ●`
- 流程输出接流程输出；
- 逻辑输入接逻辑输入。

只有明确声明为混合节点的节点，才可以同时拥有流程接口和逻辑接口。

## 5.4 接口视觉

### 流程接口

- 圆形端口；
- 蓝色或青蓝色连线；
- 连线较粗；
- 表示控制权移动。

### 逻辑接口

- 菱形端口；
- 琥珀色、金橙色或同等高可读色；
- 连线略细，但必须在深色背景中清晰；
- 不使用难以辨认的灰色；
- 表示状态引用和逻辑关系。

颜色不是数据类型兼容系统，只是“流程 / 逻辑”两种语义的视觉区分。

# 6. 统一 Graph Editor

0.3.0.0 只能有一套 Graph Editor 交互语言。

Story Flow、会话局部图和任务局部图必须共享：

- 左键选择和拖动节点；
- 框选；
- 中键平移；
- 鼠标位置中心缩放；
- 右键菜单；
- 输入端和输出端均可发起连接；
- 已有连接双端重接；
- 拖到空白处断开；
- Esc 取消；
- Undo / Redo；
- Copy / Paste；
- Delete；
- 动态端口；
- Problems 定位；
- 节点内参数编辑；
- 节点参数折叠。

差异只允许是：

```text
当前图允许出现哪些节点
当前图允许使用 ●、◆ 中的哪一种接口
```

不得为 Task Graph 设计另一套固定列布局、另一套布线规则或另一套交互手势。

0.3.0.0 不实现：

- 转接点；
- 线路 Junction；
- Task 专用布线系统；
- 并发节点；
- 多执行游标。

# 7. Story Flow 规格

## 7.1 【开始】触发配置

【开始】节点支持动态触发槽。

每个触发槽保存：

```text
port_id
display_name
trigger_type
trigger_properties
order
```

例如：

```text
角色交互：酒馆老板
进入区域：森林入口
进入剧情
```

外部显示为多个具名 `●` 流程输出。

同一个触发输出仍然只能连接一个目标。

## 7.2 重复策略

【开始】节点或 Story Inspector 提供：

```text
重复策略
- 仅一次
- 可重复
- 每日重复
- 冷却后重复
```

0.3.0.0 必须实现的最低集合：

- 仅一次；
- 可重复。

每日重复和冷却后重复若无法在本里程碑可靠完成，可以保留 Schema 和 Inspector，但必须明确标为未启用，不能伪装成可用功能。

无论重复策略是什么：

```text
同一玩家 + 同一 Story ID
同时最多一个 Active 实例
```

## 7.3 聚合【会话】节点

Story Flow 中的【会话】节点由一个 Session Resource 生成。

外部端口：

```text
1 个 ● 流程输入
0 或 1 个 ◆ 逻辑输入
N 个 ● 流程输出
M 个 ◆ 逻辑输出
```

其中：

- `●` 输出来自会话内部命名【结束】；
- `◆` 输出来自会话内部命名【逻辑输出】；
- 可选 `◆` 输入进入会话内部【起始】的逻辑输出。

## 7.4 聚合【任务】节点

Story Flow 中的【任务】节点由一个 Task Resource 生成。

外部端口：

```text
1 个 ● 流程输入
N 个 ● 流程输出
M 个 ◆ 逻辑输出
```

其中：

- Story 流程进入 `●` 输入时，激活 TaskInstance；
- `●` 输出来自任务内部【结算】的具名输入槽；
- `◆` 输出来自任务内部【逻辑输出】；
- Task Active 时，目标状态通过事件驱动更新；
- 【结算】产生唯一结果后，Task 停止并从对应 `●` 输出继续 Story Flow。

## 7.5 Story Flow 条件节点

Story Flow 中的【条件】是混合节点：

```text
1 个 ● 流程输入
1 个 ◆ 逻辑输入
2 个 ● 流程输出：是 / 否
```

语义：

- `●` 决定什么时候进行判断；
- `◆` 决定判断依据；
- true 走“是”；
- false 走“否”。

不得要求用户填写内部变量名、表达式字符串或代码。

## 7.6 Story Flow 单流程原则

Story Flow 只维护一个确定的控制流程。

- 条件节点每次只选择一个流程输出；
- 会话每次只选择一个结束结果；
- 任务结算每次只选择一个结果；
- 不存在隐式扇出执行；
- 不存在隐藏并发。

# 8. 会话局部图规格

## 8.1 节点集合

0.3.0.0 会话图最低节点集合：

```text
【起始】
【台词】
【选择】
【条件】
【与】
【或】
【非】
【逻辑输出】
【结束】
```

旧 Jump 数据需要兼容加载，但不必作为主要新建节点公开。

## 8.2 【台词】

最低字段：

```text
speaker_actor_id
text
```

端口：

```text
1 个 ● 输入
1 个 ● 输出
```

Speaker 使用项目 Actor 选择器，不以手写 ID 作为主交互。

## 8.3 【选择】

最低字段：

```text
prompt
options[]
```

每个选项保存：

```text
option_id
display_text
flow_port_id
```

端口：

```text
1 个 ● 输入
N 个具名 ● 输出
```

每次会话只允许一个选项成为本次流程结果。

会话内部需要支持把选项选择状态提供给逻辑网络。实现可以由【选择】节点提供稳定的选项逻辑状态，供【逻辑输出】引用，但不得向用户暴露底层变量名。

## 8.4 【结束】

每个【结束】保存：

```text
port_id
display_name
```

规则：

- 一个 `●` 输入；
- 名称在当前会话公开接口中唯一；
- 外部聚合【会话】节点显示同名 `●` 输出；
- 改名不破坏已有连接；
- 删除被外部使用的【结束】时必须列出引用并确认。

## 8.5 会话逻辑输出

每个【逻辑输出】保存：

```text
port_id
display_name
```

规则：

- 一个 `◆` 输入；
- 映射为外部聚合【会话】节点的 `◆` 输出；
- 可以引用选项状态、条件组合或会话内部其它逻辑状态；
- 改名不破坏外部连接；
- 删除时检查外部引用。

## 8.6 会话运行语义

```text
Story Flow 进入【会话】
→ 创建或启动一次 SessionInstance
→ 从【起始】的 ● 输出开始
→ 台词 / 选择 / 条件
→ 进入某个【结束】
→ 关闭本次会话
→ Story Flow 从对应 ● 端口继续
```

会话是同步短流程，不支持：

- 外部重入；
- 入口节点；
- 返回节点；
- 会话运行中同时启动第二个会话游标。

# 9. 任务局部图规格

## 9.1 Task 内部是纯逻辑图

任务局部图只允许 `◆` 逻辑接口。

禁止出现：

- `●` 流程接口；
- Story 触发器；
- 会话；
- 奖励动作；
- Story 跳转；
- 流程条件节点；
- 并发节点。

## 9.2 【激活】

固定唯一。

```text
0 个输入
1 个 ◆ 输出
```

状态：

```text
Task 未激活 → false
Task Active → true
Task 结算后 → false
```

【激活】可以连接多个【目标】的启用输入，因为 `◆` 输出允许一对多。

## 9.3 【目标】

最低目标类型：

- 击杀目标；
- 收集目标；
- 交互目标。

旧 ReachLocation 保持兼容，可在后续作为正式目标恢复。

每个目标至少有：

```text
1 个 ◆ 启用输入
1 个 ◆ 完成状态输出
```

激活规则：

- 启用输入第一次变为 true 时进入 Active；
- Active 后通过 Runtime 事件更新进度；
- 目标完成后输出 true；
- 同一 TaskInstance 内不自动重置；
- Task 结算或 Story 终止时停止更新。

这允许自然表达顺序目标：

```text
【激活】◆
→【目标 A】◆完成
→【目标 B】的启用输入
→【目标 B】◆完成
→【目标 C】的启用输入
```

也允许同时激活多个目标：

```text
【激活】◆
├→【目标 A】
├→【目标 B】
└→【目标 C】
```

不需要“并发”节点。

## 9.4 与 / 或 / 非

作为纯逻辑组合器使用。

一个逻辑输入永远只有一个来源。

多条件组合只能显式通过这些节点表达。

## 9.5 【逻辑输出】

一个任务可以有多个【逻辑输出】。

例如：

```text
Boss 已击杀
可交付
隐藏目标完成
未使用药水
```

规则：

- 一个 `◆` 输入；
- 外部映射为一个具名 `◆` 输出；
- 不推动 Story；
- 不结束 Task；
- Task 未激活时仍可查询，但依赖目标的默认状态为 false；
- Task Active 时随内部状态更新；
- Task 结算后保留最终快照，直到当前 StoryInstance 被清理或新一轮 Story 创建。

## 9.6 【结算】

固定唯一。

用户可以创建多个结果槽：

```text
1. ◆ 完美完成
2. ◆ 普通完成
3. ◆ 失败
```

每个槽保存：

```text
port_id
display_name
order
```

判定规则：

1. 仅在 Task Active 时具有结算效力；
2. 每次相关逻辑状态变化后重新求值；
3. 从上到下检查；
4. 第一个为 true 的结果获胜；
5. 本轮停止继续判断；
6. Task 状态保存唯一结果；
7. 所有目标停止工作；
8. 对外仅发送对应的一个 `●` 流程信号；
9. 全部为 false 时保持 Active。

结果优先级不是隐藏配置，而是【结算】节点输入槽从上到下的可视顺序。

用户可以拖动槽位重新排序。

## 9.7 结算槽与外部端口

内部：

```text
【结算】
1. ◆ 完美完成
2. ◆ 普通完成
3. ◆ 失败
```

外部聚合【任务】节点：

```text
● 完美完成
● 普通完成
● 失败
```

改名或排序：

- 连接绑定稳定 `port_id`；
- 改名不会断线；
- 排序不会断线；
- 外部端口显示顺序同步；
- 删除被外部使用的槽位时必须警告和确认；
- 同一任务所有公开端口名称不得重复。

## 9.8 任务与条件的区别

### 普通逻辑条件

回答：

```text
现在是否满足？
```

通常是即时、隐藏、不会进入玩家任务日志的状态。

### 【目标】

回答：

```text
这个任务激活以后，玩家完成到什么程度？
```

它具有：

- 激活时间；
- 玩家归属；
- 进度；
- 持久化；
- 完成状态；
- 任务日志显示。

默认规则：

```text
普通条件 = 隐形逻辑
任务目标 = 显性玩家目标
```

未来可允许隐藏目标，但不改变 Task 与普通条件的生命周期差异。

## 9.9 事件驱动性能模型

目标节点不得各自每 Tick 扫描全部状态。

Runtime 应使用统一事件路由：

```text
Minecraft 事件
→ Story / Task Event Bus
→ 玩家
→ 事件类型
→ 目标类型 / 目标 ID
→ 仅更新相关 Active 目标
```

示例：

- Kill 目标监听实体死亡事件；
- Interact 目标监听角色交互事件；
- Collect 尽量监听物品获得 / 背包变化；
- Region / Timer 使用集中调度器，而不是每个目标各自开 Tick。

任务局部图对用户只显示【目标】，不出现“监听器 / Hook”节点。

# 11. 数据模型

## 11.1 通用 Graph 连接

连接必须显式保存接口类型与稳定端口 ID：

```json
{
  "from_node_id": "node_a",
  "from_port_id": "port_x",
  "to_node_id": "node_b",
  "to_port_id": "port_y",
  "interface_kind": "flow"
}
```

`interface_kind`：

```text
flow
logic
```

连接不得依赖显示名称。

## 11.2 公开端口

动态公开端口统一保存：

```text
port_id
display_name
order
kind
```

适用：

- Story【开始】触发槽；
- Session【结束】；
- Session【逻辑输出】；
- Task【结算】槽；
- Task【逻辑输出】。

## 11.3 稳定 ID

必须保证：

- 改名不使外部连接断开；
- 排序不使外部连接断开；
- 节点移动不改变端口身份；
- Duplicate 产生新资源 ID 和新内部 ID；
- Reference 保持同一个资源和端口身份。

## 11.4 名称唯一性

同一资源的所有公开端口显示名必须唯一。

例如同一个 Task 不允许同时出现：

```text
结算槽：完成
逻辑输出：完成
```

即使接口形状不同，也容易造成外部理解混乱。

## 11.5 逻辑图无环

由 `◆` 组成的组合逻辑网络必须是有向无环图。

尝试形成逻辑环时，Studio 直接拒绝连接。

禁止：

```text
A → 非 → A
与 → 或 → 与
```

有状态的【目标】是逻辑源，不允许通过组合逻辑回写自身状态。

# 12. Runtime 执行模型

## 12.1 StoryInstance

主键：

```text
player_uuid + story_id
```

同一时间最多一个 Active。

保存：

- Story 状态；
- 当前流程节点；
- 当前会话调用状态；
- 当前任务实例；
- Story 逻辑状态；
- 重复策略信息。

0.3.0.0 必须解决旧版本 Story 游标仅内存保存的问题，至少使活动 Story 能在服务器保存 / 重启后恢复。

## 12.2 SessionInstance

一次聚合【会话】节点调用创建一次 SessionInstance。

保存：

- session_resource_id；
- 当前台词 / 选择节点；
- 已选择选项；
- 当前内部逻辑值；
- 最终结束 port_id；
- 对外逻辑输出快照。

会话结束后，Story 从唯一结束结果继续。

## 12.3 TaskInstance

主键至少包括：

```text
player_uuid
story_instance_id
task_node_placement_id
task_resource_id
```

一个 StoryInstance 中同一个 Task 节点最多一份 TaskInstance。

状态：

```text
NotStarted
Active
Settled
CancelledByStoryTermination
Error
```

保存：

- 目标激活状态；
- 目标进度；
- 目标完成状态；
- 逻辑输出快照；
- 唯一结算结果 port_id；
- 激活与结算时间。

## 12.4 任务重新进入

0.3.0.0 不允许同一个 StoryInstance 中创建同一 Task 节点的第二份实例。

若流程因显式循环重新进入：

- Active：继续等待同一实例，不重置；
- Settled：返回已保存的结算结果；
- 不重新激活目标；
- 不产生第二次任务日志条目。

## 12.5 Story 终止

进入【终止】时：

- StoryInstance 进入终态；
- Active Task 全部取消；
- 活动 Session 关闭；
- 取消相关事件订阅；
- 保存最终状态；
- 根据重复策略决定未来是否可再次启动。

# 13. 2.1.3 向 0.3.0.0 迁移

0.3.0.0 是重大架构更新，必须提供有备份的迁移。

## 13.1 会话迁移

旧 Dialogue：

```text
entry
line
choice
jump
end
next
result
```

迁移为 Session Graph：

- 创建唯一【起始】；
- 将旧 entry 与【起始】连接；
- Line →【台词】；
- Choice →【选择】；
- End → 命名【结束】；
- result 迁移为公开 flow port；
- Jump 迁移为兼容节点或直接转换连接；
- 旧节点 ID 尽量保留；
- 创建编辑器位置；
- 不改变文本和选项语义。

## 13.2 任务迁移

旧 Quest：

```text
Objectives
ObjectiveGroups
ALL / ANY / SEQUENCE
```

迁移为 Task Logic Graph：

### 单目标

```text
【激活】
→【目标】
→【结算：完成】
```

### ALL

```text
多个【目标】
→【与】
→【结算：完成】
```

### ANY

```text
多个【目标】
→【或】
→【结算：完成】
```

### SEQUENCE

转换为目标启用链：

```text
【激活】
→【目标 1 状态】
→【目标 2 启用】
→【目标 2 状态】
→【目标 3 启用】
→【结算：完成】
```

旧 Objective ID、进度语义和玩家日志文本尽量保留。

## 13.3 Story Flow 迁移

旧 Story Flow 中：

- `StoryStart` →【开始】；
- `End / EndStory` →【终止】；
- `PlayDialogue + DialogueExitBranch` 在结构明确时合并为聚合【会话】；
- `StartQuest / QuestCompleted / QuestState` 在结构明确时转换为聚合【任务】和逻辑引用；
- 旧 ActorInteract / EnterRegion / 动作节点继续映射；
- 无法安全自动迁移的结构必须生成“迁移问题”，不能静默猜测。

## 13.4 迁移安全

必须：

- 创建 `.migration-backups`；
- 使用事务式写入；
- 迁移失败时恢复全部原文件；
- 保留迁移日志；
- 不在用户无感知时破坏旧项目；
- 提供只读迁移预览；
- 允许用户先复制项目再迁移。

# 14. 仍然存在的明确边界

## 14.1 任务期间的中途会话

0.3.0.0 不引入：

- Task 入口；
- Task 返回；
- Task 内部会话；
- Story 多执行游标；
- Task 非终止回调。

因此，当 Story Flow 正在等待一个 Active Task 结算时，同一 Story 不能同时执行另一条“未完成提示会话”分支。

完成汇报可以通过 Task 中的“与 Boss 交互”目标表达：

```text
击杀目标完成
→ 激活交互目标
→ 玩家与 Boss 交互
→ Task 结算
→ Story Flow 播放完成会话
```

玩家在目标完成前与 Boss 交互的“尚未完成”反馈，0.3.0.0 若需要，必须由：

- 独立 Story；
- Actor 级通用交互系统；
- 后续专门设计的事件反应层；

之一处理。

Codex 不得为了这个用例重新引入已否决的入口 / 返回 / Task 内嵌会话。

## 14.2 无隐式并发

0.3.0.0 不支持一个流程信号同时启动多条有副作用的流程。

多个任务目标同时活跃，来自：

```text
【激活】的 ◆ 输出可一对多
```

不是来自流程并发。

# 21. Codex 执行纪律

Codex 在实施 0.3.0.0 时必须遵守：

- 不得重新引入已经否决的架构；
- 不得用临时列表 UI 伪装局部节点图；
- 不得只做 Studio 视觉而不做 Runtime；
- 不得只做 Runtime 而让 Studio 生成无效数据；
- 不得用内部变量输入框代替 ◆ 可视化逻辑；
- 不得让 Task 内出现会话；
- 不得让 Task 内出现 ●；
- 不得让一个 Task 结算同时触发多个 ●；
- 不得让一个玩家同时拥有同一 Story 的两个 Active 实例；
- 不得通过静默数据改写完成迁移；
- 不得以测试文档代替 Runtime、真窗口或 Forge 验收；
- 不得把 CNPC 专属绑定、最终 NPC 体验、剧情包部署或最终任务 UI 扩入 0.3.0.0；
- 不得只提交本地而不推送 GitHub。

0.3.0.0 的验收标准不是“页面已经出现”，而是：

> 创作者能够以 Story Flow 为主工作台，从资源树创建并拖入会话和任务；会话能够以台词 / 选择图运行；任务能够以纯逻辑目标图运行；● 与 ◆ 的语义从 Studio、JSON 到 Runtime 完全一致；Story Flow、Session、Task、Objective、Action、终止、持久化与清理在 Runtime 中形成完整稳定闭环，并能在 Forge / Minecraft 环境中保持兼容运行。最终 CNPC/NPC/任务 UI 产品体验属于 0.3.1.0。
