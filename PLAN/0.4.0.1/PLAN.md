## 4. WP-A：指名表容量与读写一致性

### 4.1 问题用途及准确归因

[已知事实] `NominatorSavedData` 保存具体实体的选择／群组信息。它不是 Studio 资源目录：一个集体角色可以对应许多实体 UUID。当前 reader 将实体记录数限制为 `NominatorCatalog.MAX_ENTRIES`（512），而 `put()`／`writeToNBT()` 没有对应限制；正常绑定服务也没有先拒绝新增第 513 条。[A01 §2][S09]

这在 0.3.3.7 已存在，不归罪于 0.4.0.0 清扫。不需要恢复实体种类自动归组来解决规模问题。

### 4.2 必须建立独立、可解释的容量合同

[施工要求]

- 将**世界实体绑定的存储容量**与**目录／网络传输的条目限制**分开；不得只是更改 `NominatorCatalog.MAX_ENTRIES`，顺便扩大所有网络包预算。
- 使用一个有名称、单一来源的存储限制 `L_BIND`（本文为概念名），reader、写入 API、服务级预检和 writer 防线遵循同一合同。
- P0 根据现有字段上限、真实 NBT 大小和有界验证确定具体值与安全余量。本文不把 512、513、某个任意大数或“无限”冒充用户需求。
- 优先消除目录容量误用于世界容量的耦合。若最终仍采用 512，必须有独立存储依据，不能只因为旧常量恰好是 512；同样不能只把拒绝点挪到写操作，就宣称支持了更大世界规模。
- 若计量显示需要额外字节预算，先定清“未压缩编码量／压缩文件量／字段预算”的用途，确保写入可接受范围不大于读取可接受范围。不得因每帧重复全表编码引入明显开销。

本版最低安全目标是读写一致，而不是承诺任意数量实体。512／513 实验必须重新运行，最终表现按明确的 `L_BIND` 判断：**要么合法接受并可重读，要么在任何相关修改前明确拒绝。绝不能成功写出再在重启时拒绝。**

### 4.3 不可破坏的操作不变量

| 场景 | 必须行为 |
|---|---|
| 新增 UUID | 对最终结果预检；超限不修改任何相关持久对象、不增加 revision、不返成功 |
| 更新已有 UUID | 按实际净变化判断，不能“表满就禁止所有编辑” |
| 原位重复指名／no-op | 幂等，不消耗额外条目；不能产生虚假失败或无意义 revision |
| 解绑／删除记录 | 允许合法减量，不能因已达容量就阻止用户释放记录 |
| 个体角色显式转移 | 计算源宿主清理与目标新增后的最终状态；失败时原宿主、组、个体身份全部保持 |
| 转移后旧宿主还有集体角色 | 旧记录未必会消失，不能错误按“转移必定净零”放行 |
| 并发／过期请求 | 沿现有服务端线程与 revision 校验，不绕过版本检查或产生先检查后变更竞态 |
| 达不到读取预算的当前数据 | 保留原文件并报具体原因；不截断列表、不只加载前 N 个、不转为空表 |

### 4.4 前置检查必须跨越实际两个状态拥有者

沿 `NominatorActions → NominatorService.bindEntity → NpcIdentitySavedData / NominatorSavedData` 检查实际修改顺序。[S10]

仅在 `selections.put()` 内检查容量不够：个体身份可能此前已经被 `bind/transfer/unbindHost` 改动。正确要求是：

```text
验证权限、请求／目录／绑定 revision 与资源归属
→ 构造或计算整个操作的最终变化
→ 预检实体表容量及受影响身份条件
→ 在既有同步边界内提交
→ 只有提交完成才报告成功
```

下层 `put()` 仍要防御绕过服务直接调用的非法新增；writer 可做最终一致性断言，但**不能把首次超限发现留到自动存盘时**。预检后仍可能失败的修改，必须保持现有原子性或有可验证的最小回滚，不能返回失败却已经转走角色。

容量错误使用准确、简洁的业务错误和现有结果通道；保留 token／sequence、pending 结束与必要刷新，不新开网络协议、管理面板或自动清理流程。

### 4.5 验证方法：替身复现升级为真实存储测试

保留附件复现作为历史问题证据，但不要把其 `net.minecraft.*`、身份辅助替身复制到生产或成品中。[A02]

用仓库已有真实 Minecraft 依赖和 `MapStorage` 生成测试：

- 数量覆盖 0、1、511、512、513，以及最终 `L_BIND−1 / L_BIND / L_BIND+1`；重复点合并。
- 资源至少包含“同一个集体角色绑定许多不同 UUID”，另测个体与多组组合。
- 正向数据由当前公共操作／存储接口产生，再实际压缩写出并通过新 `MapStorage` 实例重读。不是先手写一个有 513 条的文件再声称正常作者链成功。
- 容量满额时测更新、no-op、解绑、净增／净减转移及旧宿主残留组；拒绝前后比较两份身份表的内容、revision、dirty 状态与磁盘哈希。
- 至少一轮真实专服正常保存、停服、重启，确认合法表继续解析身份并能编辑。大数量可以经测试专用服务调用生成，不要求机械手点 513 次；报告必须写清生成方法。

不把设置 `L_BIND` 很小的单测当成真实 512／513 边界验证；可以另以小容量注入测试满额路径，但两类证据分别保留。

## 5. WP-B：Session／Story 世界状态读取失败隔离

### 5.1 已知问题与未证明后果

[已知事实] `CanonicalSessionSavedData` 同时承载 Session、Story 和 continuation。审计看到初始 `bound=true`、String 构造没有待读取状态、`readFromNBT()` 先 decode 再改变 bound，且 `get(MapStorage)`／writer 没有指名表同等失败门禁。[A01 §3][S11]

新增 `line_contexts` 的单条不合法字节会被世界 codec 拒绝，可能使整份读取失败。[S12]

[待实证] “真实文件随后被默认空状态覆盖”是风险，不是本 PLAN 声称已经发生的事故。先用真实 MapStorage 验证；不只在 reader 单测中断言抛异常就关闭本项。

### 5.2 分开‘读取状态’与‘资源绑定状态’

[工程约定] 复用现有指名表的局部隔离思想，而不是构造一个新的通用 SavedData 框架。允许最小标志／枚举实现；名称可按代码调整，但必须区分下列含义：

| 状态／场景 | 可以做什么 | 不能做什么 |
|---|---|---|
| 确认磁盘记录不存在，显式新建当前数据 | 正常初始化、后续保存 | 不以“读取失败”为由进入此分支 |
| MapStorage 反射构造，待读取 | 等待当前文件读取结果 | 返回可用空实例、start／resume／dirty／写回 |
| 当前 NBT 读取成功，但资源尚未绑定 | 保留有效 `pendingRaw`；按既有只读／延迟恢复合同处理 | 把正常未绑定误判为坏数据，或提前推进剧情 |
| 读取、资源解析均成功 | 按现行业务执行 | 绕过 Story／Task／权限边界 |
| 首次读取失败／压缩流损坏／读取未完成 | 记录不可用原因，保留原字节、隔离对象 | 默认空表、自动新建替代、标 dirty、序列化回原文件 |
| 已有有效对象再次读取失败 | 保留上次有效内存以供安全诊断，进入不可用状态 | 继续当作成功更新或悄悄把旧快照当 fallback 执行 |

合法 `pendingRaw` 的无损读写能力要保留；不能把所有 `bound=false` 都封成错误。磁盘缺失、文件存在但坏、对象类型错误必须区别处理。

### 5.3 预检必须覆盖所有真正的消费者

执行者列出并保护实际读写路径，包括：`get/getOrCreate`、资源 `bind/bindAvailable`、start／resume／continue／choice、消费会话、Story 继续执行、结果路由／收据相关修改、`markDirty/setDirty(true)`、`writeToNBT`、只读诊断及其他公开包装入口。

具体方法以源码引用追踪为准；不能只改一个 `get()` 或 `start()` 后留下另一条便利方法绕过。可用性检查应先于创建／修改相邻持久数据、改变独立奖励记录或生成成功响应。

失败实例在 `MapStorage` 中即使被缓存，也必须保持失败身份；不能从缓存清掉再偷偷创建成功空实例。`setDirty(false)` 等必要的失败清理，不得反过来解除隔离。

### 5.4 写回保护必须早于触碰目标输出与原文件

失败／待读取实例的 writer 必须在修改输出 NBT 之前拒绝；真实 MapStorage 存储路径必须证明，拒绝发生在打开或截断原存档之前。不能只测试 `isDirty=false`，因为其他调用或测试可能把 dirty 设为 true。

至少覆盖：

1. 常规读取失败后保存。
2. 在隔离测试中强制 dirty，再执行真实 `saveAllData()`。
3. 保存前 NBT 放 sentinel，writer 失败后 sentinel 和原输入保持。
4. 失败后调用 getter、绑定、启动、恢复、结果处理和诊断，再保存。
5. 已有有效内存对象再次读取失败时，未提交部分不覆盖旧内存，原磁盘不被自动回退写入。

不得修改 Minecraft 的 MapStorage 类、全局吞异常或依赖“反正这次没 dirty”规避问题。[S13]

### 5.5 错误隔离粒度：先保护数据，不假装坏文件内其他状态仍可安全运行

[工程约定] 本版默认隔离**受损的这一份 Session／Story 世界状态文件及其依赖者**。若一份文件容纳多个玩家／故事，其不可用可能阻断多个相关实例；这是文件级隔离的边界，应在诊断中如实说明。

不要承诺“坏一条缓存，其余同文件故事必定照跑”，也不要为了兑现该承诺在本版增加部分恢复引擎。保持其他无关服务器操作和未依赖该文件的独立数据安全；Task 若依赖被隔离的父 Story，应保留状态并阻止不安全推进，不伪造完成或重置。

在相关事件／请求／命令边界报告稳定错误并受控结束本次操作；避免异常逃逸击穿服务端 tick，也避免每 tick 重试／刷屏。使用现有边界和最小重复日志抑制，不新建常驻告警服务。

实体指名表、Item 表、其他 Mod 文件和正常世界数据不能被此错误顺带删除／重建。诊断不把“数据不可用”显示成“该玩家没有故事”。

### 5.6 `line_contexts` 的处理边界

这份缓存是已认可的 Choice 恢复机制，本版保留。默认沿用严格读取规则，**不自动删坏缓存、不跳过条目后把其余状态写回原文件、不重算动态正文假装修复**。

若实现者提出独立隔离展示缓存且继续运行，这将改变本节默认故障合同，应先说明对前文、头像、游标、动态文本冻结和奖励的影响；不能作为隐藏 fallback 顺手实现。本版可以在整体失败隔离正确后完成，不要求增加自动恢复产品。

有效当前缓存须继续满足：

```text
恢复相同活动会话
→ 静默 LINE 上下文
→ 当前 CHOICE
→ 保留身份与已确认正文
→ 不重复声音／画面／历史，也不改变权威执行游标
```

缺少可选缓存的有效当前存档，按既有合同读取；不能重新补出作者已删除的 prompt 或凭空编造缺失前文。[S03][S05]

### 5.7 真实故障向量与验收

使用包含至少两个当前 Story／Session 状态的隔离世界副本。每种故障单独复制，先记录两份世界状态／相关收据的哈希和可读状态，再注入：

| 向量 | 应证明的边界 |
|---|---|
| 坏 gzip／截断压缩数据 | 尚未进入 `readFromNBT()` 也不能留下可用空对象 |
| 错误 root／schema／字段类型 | 当前 reader 拒绝后不可写回，不恢复退休 reader |
| 非法 Session／Story 实例记录 | 没有半份加载当成功或部分覆盖 |
| 单项 `line_contexts` 字节损坏 | 明确阻断受影响文件，而不是空成功／删缓存后继续 |
| context 的 transport／Story／Session 对不上 | 在既有解码／使用边界受控拒绝，不串上下文 |
| 有效已加载对象再次读坏输入 | 状态隔离、旧内存未被部分替换、后续 writer 受阻 |
| 文件真正不存在 | 新世界正常创建，不能把全部首次启动都修坏 |
| 有效 pending、活动 LINE／CHOICE／continuation | 正常保存、资源绑定及重启恢复仍成立 |

自动测试用真实 Minecraft 类／MapStorage；集成服务器和专服各做至少一条关键失败链，检查后续普通服务器操作正常。仅测试最小替身或只断言异常不能代替实际存储证据。

停服后可在**隔离样例**中显式放回已知有效的当前备份并重新启动，证明正常路径可恢复。不得把此测试写成面向用户的自动迁移或修复功能。

## 7. WP-D：有限实机验收，不为了凑 PASS 造功能

### 7.1 四种证据分别标注

| 标记 | 真正证明什么 |
|---|---|
| A | 自动／头less 逻辑、编解码或有实际 Minecraft 类的 Probe；须注明是否测试替身 |
| M | 实际游戏／服务端运行与存盘、重启、操作结果；自动驱动也要说明来源 |
| W | Windows 正式候选上的真实键鼠／UIA 作者操作；不是仅调用 ViewModel |
| H | 人工确实听到并核对声音；命令排队、日志、音频文件存在均不能代替 |

同一用例可有多个标记，但不可相互冒充。测试专用生成数据、修改负向 fixture、真实 Studio 导出和手工编辑 JSON 必须分开说明。

### 7.2 物品附加过滤：关闭真正缺口，取消虚假的作者前提

[已知事实] 上一轮报告已验证自动过滤，但 `metadata/damage` 的原生作者链未完成，且记录称基线／当前没有相应编辑入口。[A01 §7][S02][S04]

本版按以下路径处理：

1. 对照固定基线与当前分支，核验节点内和 Inspector 是否真的存在该字段的正式编辑入口，记录具体代码／界面依据。
2. **有正式入口**：通过该入口创建含额外条件的任务，实际保存、导出、部署，验证候选展示、收集计数和提交扣除一致。
3. **无正式入口**：这一步记录为 `N/A_NO_AUTHORING_ENTRY`，附依据；不新增界面，不假称用 UI 填过 metadata。现行底层过滤行为仍须验证，不能整个 R4 直接 N/A。
4. 使用当前 schema 的受控 fixture，在真实 Forge 库存／提交链验证允许与排除的 damage、个体／EXACT／FUZZY 组、跨槽计数、数量不足不扣、候选与实际匹配一致。不能恢复原生注册名目标。
5. 正常 UI 导出包与注入附加过滤的 fixture 分别记录路径、来源和 hash；后者不能冒充前者的“同一份导出字节”。

这样关闭的是“现有过滤机制与其验证边界”，不是偷偷增加作者功能。`N/A` 仅适用于不存在的操作步骤，不能用于真实存储风险或可达但没测的路径。

### 7.3 人工听音

准备一个很小的当前演出样例：可区分的语音／音效、循环背景音乐、含本地分屏的台词及后续 Choice；媒体有明确使用权。使用被测正式 JAR、客户端音频输出设备及该样例的实际包字节。

最少核对：正常语音与 BGM 可闻；两类 DGR 音量的静音作用各自正确；Minecraft 主音量为零时静音；本地翻显示页不重播／提前停止当前原句声音；真正进入下一句按现有规则处理；Choice 冷恢复不重复语音／画面；离服／关闭上下文无残留播放。

不重做留声机、在线音乐解析或音频后端。只有本版真改动到共享链时补一个相应留声机回归，不能把 QQ／网易云外部服务可用性做成本版前提。

H 记录注明听音人员、设备、候选 JAR、包 hash、实际动作及结果。没有可以执行听音的人员或设备时，状态为 `NOT_RUN/BLOCKED`，集中提交一次有限人工核验请求；工程可以继续，不能把该项计为 PASS，也不能声称全验收闭合。

### 7.4 环境与故障边界的最小覆盖

不是把所有游戏环境×所有操作排列组合。至少形成以下有限覆盖：

| 环境／链 | 本版必测重点 |
|---|---|
| 原版单人集成服务器 | 当前正常 Story→Session→Choice→Task 基础链；一条 Session 损坏存档拒绝路径；普通操作不被异常击穿 |
| 原版专服＋匹配客户端 | R1 合法容量表保存停服重启；R2 故障隔离与原文件保留；双玩家状态不串用 |
| 正式 JAR＋CNPC 专服或单人 | 具体真实 NPC 指名、集体角色、显式转移、解绑、重新指名；选一条与实际工具边界相关的拒绝路径 |
| 开发客户端＋实际 CNPC 环境 | 补上一轮尚缺的针对性完整操作链：上述实体操作＋个体物品／精准／模糊组，保存重启后恢复；不使用开发桩冒充真实 CNPC |
| 各直接读取相关存档的工具／命令 | 先按真实调用边界分组；每条不同边界自动故障覆盖，每类有风险的 GUI／命令／实体工具至少一个原生代表 |

“全套操作链”仅指本表列出的有限动作，不代表所有世界条件均已验证。没有改第三方 JAR，没有拿原版村民代表真实 CNPC 宿主，没有拿主菜单代替进入世界操作。

复制器、收纳箱、解绑、诊断和命令等是否共用同一错误边界，以源码事实决定；不得先写“全部已覆盖”。若出现实际未捕获异常，定点修复边界；不在全局 tick 加吞所有异常的兜底。

### 7.5 Studio 剩余交互回归

不重新改造已认可的拖动效果。在正式候选上，以一个小项目和一个只读引用组完成：

- 有筛选搜索时的排序、真实鼠标离开／返回、Esc 取消、窗口失活和工作区切换；取消前后不提交额外排序。

- 资源列表排序后仍可拖到画布及准确参数框；一次有效落下对应一次 Undo，取消不污染 dirty／文件。
- 保存重开、Undo／Redo 后顺序稳定；需要时更新引用包，确认公开端口可见状态正确刷新。

每种不同取消边界保留一个真实样例，配合已有自动覆盖；不要求重新录制所有像素位置，也不因某个组合未测就宣布整个拖动系统有缺陷。

### 7.6 同一份正常导出包的最终运行闭环

记录导出文件 hash，将同一批字节放入对应隔离游戏环境；验证具体身份、会话选择、当前背包收集、角色提交、一次奖励、无内容修改 reload、重连、正常停服／重启。另验证普通 Disabled 对新旧实例的区别与零结算不自动完成，作为本版状态修复的保护样例。

容量压力 fixture、损坏存档、附加过滤 fixture 与这组正常包分别标注，不能相互替代证据。

### 8.2 最小可复查证据

最终证据至少包含：

| 内容 | 必要字段 |
|---|---|
| 测试执行 | 实际命令、环境、开始／结束时间、退出码、PASS／FAIL／SKIP 数，关键行为组是否执行 |

| 实机样例 | 程序 hash、包 hash、环境、实际操作、观察结果；自动驱动和人工动作分别注明 |
| 来源与构建 | 实际编译源码清单、构建脚本／锁文件／测试输入清单、基线+patch 或准确实现提交 |
| 成品对应 | JAR、EXE、主 DLL、Core DLL、程序白名单的路径／大小／版本／SHA-256 |
| 部署保护 | Data 更新前后清单及 hash、程序候选与权威副本逐项比对结果 |

报告应可从现有日志／TRX解析，而不是凭记忆手填通过数。原始文件保留，公开摘要脱敏；小规模证据整理不要求上传整个世界、全部图片、个人路径或第三方文件。

此前 0.4.0.0 只有本地原始证据的做法不意味着造假。此版改进的是后续复查能力，不为补证据重新发布／重打包旧版本。[A01 §7][S02]

### 8.3 防止‘测完又换了一份程序’

冻结待交付生产差异和测试输入，构建唯一候选，再执行最终测试。最后若修改生产／协议／界面代码，重新执行受影响测试并更新对应二进制及证据；不能用先前通过报告覆盖后改的源码。

只追加说明或脱敏记录的提交，可以不重新构建未变产物，但明确“实现提交／已编译源码指纹”和“后续文档提交”的区别。不能要求一个提交在自身文件里预写自己的 SHA，也不能只留一个早期 implementation_commit 让读者猜最终代码是哪份。

生产来源清单不能漏未跟踪文件；测试、构建任务和 fixture 也需能够定位。工作区行尾与 Git blob 字节可能不同，选择一种明确的清单口径并记录实际编译输入，不能把两种 hash 随意混用。

### 8.4 完整构建与开发产物

按照当前 `docs/BUILDING.md` 和仓库规范完成 Runtime 正式构建、必要 Probe、完整 Core／WPF 及 Windows x64 自包含 Studio。[S06][S07][S08]

测试数量减少或增加都必须有原因；不以数量等于 0.4.0.0 为目标。跳过项逐个注明是否受本版影响。与修复直接相关的 mandatory 测试不能靠 SKIP 关闭；无关既有媒体环境项可如实保留限制。

本版不改便携结构：根 apphost EXE，`Program/Tools/Docs/Data` 分类保持。正式 Runtime 为 `build/libs/darkgrey_rpg-0.4.0.1.jar`；dev／sources 不是用户安装 JAR。[S08]

### 8.5 权威 dist 提升与 Data 保护

更新前让用户保存并关闭目标 Studio；核实真实窗口／进程状态，不凭一个残留 PID 强杀。未关闭时保持候选可交付状态，报告待部署，不把候选说成权威更新。[S07]

使用现有 `studio/package-studio.ps1` 的候选目录与提升方式，只更新程序白名单；不递归清空整个 Studio，不覆写未知文件。部署前后在应用关闭状态比较 Data 的路径、大小及 SHA-256；用户项目、媒体、恢复文件与偏好保持。

权威入口按现有仓库合同仍为：

```text
E:\Java\MinecraftMod\DarkGreyRPG\dist\DarkGreyRPGStudio\DarkGreyRPGStudio.exe
```

在其他合法开发副本上的构建不能虚称已更新这一路径。至少核验 EXE、主 DLL、Core DLL 和全部程序白名单；根 EXE 字节变化或不变化都不能单独证明功能版本。真实游戏验证用匹配的最终 JAR，不把测试桩或旧 mods 残留混入。[S06][S07]

只用隔离解压／候选副本做启动、项目与媒体工具 smoke；不得通过启动权威副本改用户项目来证明“数据保留”。程序正常启动后的日志新增与部署写入分开统计。

### 8.6 发布与回退说明

0.4.0.1 本轮默认交付开发 dist 和验证记录，不创建 Release。用户以后明确要求成品打包时，再按 release skill 新建版本化成品，保留 `v0.4.0.0` 的标签和资产。

回退说明必须同时提到匹配程序与世界／DGR 数据备份。即使格式不变，0.4.0.1 可能允许 0.4.0.0 reader 无法处理的更大绑定表；**不能承诺只换回旧 JAR 就安全**。测试与用户操作均不自动降级、删表或缩减记录。

## 11. 完成条件与不能被包装成‘完成’的情况

### 11.1 代码实施完成

WP-A／WP-B 的读写与失败边界已经实现且正反测试通过；WP-C 的当前断言有去向并实际运行；本版改动没有恢复旧业务或误删现役功能。不能因源码能编译就签署此状态。

R1／R2 不能作为“已知限制”长期挂在本版完成声明后；若有确证说明某个风险不成立，也必须附真实加载／保存证据，且失败无写回保护的验收成立。

### 11.2 技术验收闭合

本 PLAN 的适用 mandatory 项均通过，真实存储／有限实机／作者／听音证据按要求存在。确证不存在的作者入口可以按 §7.2 精确记 N/A；其他因没设备、没执行或没修好的项目不能 N/A。

人工听音未执行时，可报告“代码实施完成、开发产物已交付、听音待确认”，不能报告“0.4.0.1 全量验收通过”。其他有限原生项同理。

### 11.3 开发交付完成

达到仓库的权威 dist 更新、程序一致性与 Data 保护要求。若目标 Studio 未关闭或无法访问权威路径，保持 `CANDIDATE_READY / DELIVERY_PENDING`，不把隔离目录当作权威交付。

### 11.4 用户接受与公开发布

用户明确接受后才更新 `user_accepted`。公开发布只是分发动作，不自动证明用户验收，也不自动关闭残余问题。

最终给用户的说明只需清楚回答：**修了什么、两个存档边界实际怎么验证、哪些当前功能回归通过、还有什么没测、正在使用的程序在哪里。** 不把几十份原始日志变成用户必须自己读的作业。
