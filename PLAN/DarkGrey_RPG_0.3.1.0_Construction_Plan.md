# DarkGrey_RPG 0.3.1.0 施工 PLAN

> 版本定位：**Minecraft 游戏内落地与完整运行版本**
>
> 0.3.0.0 解决“RPG 内容如何在 Studio 中被真正编排并由 Runtime 跑通”。
>
> 0.3.1.0 解决“这些内容如何作为故事包进入 Minecraft、绑定真实实体与物品、在服务器上按玩家独立运行，并通过统一的逻辑接口完成跨故事协作”。

---

## 0. 总原则

0.3.1.0 必须以 **“落地 0.3.0.0 的编制框架”** 为唯一核心目标。

本版本不应重新发明第二套 Story / Session / Task 语言，也不应把范围扩展成完整 NPC 沙盒模组。所有新增系统都应服务于以下闭环：

**Studio 创作故事 → 导出故事包 → 服务器/单机加载 → 指名现实实体与物品 → 玩家触发故事 → 会话 → 任务 → 动作 → 结算 → 玩家独立持久化 → `/dgr reload` 热更新**

### 0.1 必须坚持的架构原则

1. **DarkGrey_RPG 是独立 RPG 模组**
   - 不依赖 CustomNPC+ 才能运行。
   - CNPC 只作为可选兼容对象。
   - DGR 的 Story、Session、Task、Journal、Dialogue GUI、身份系统、故事包系统均归 DGR 自己所有。

2. **中文产品术语统一**
   - 中文 UI 中“剧情”统一更名为 **“故事”**。
   - Story Flow = **故事流程**
   - Story Graph = **故事图谱**
   - Story Package = **故事包**

3. **服务端权威**
   - 故事推进、任务进度、会话状态、奖励、身份绑定、故事包加载等均由服务端裁决。
   - 普通客户端不能自行安装故事包并让服务器接受。

4. **玩家默认独立进度**
   - Story、Task、Objective、会话重要选择、奖励领取等默认按玩家 UUID 独立持久化。

5. **维度不隔离故事状态**
   - 主世界、地狱、末地共享同一玩家 Story/Task 运行状态。
   - 只有当某个目标/条件显式要求维度时，维度才参与判断。

6. **统一 Graph Editor**
   - Story、Session、Task 使用同一套画布交互、端口视觉与连线规则。
   - 区别仅在于允许出现的节点类型不同。

# 3. 【角色】系统

## 3.1 【角色】只保存故事身份

角色资源不得保存：

- 血量
- 皮肤
- 模型
- 攻击
- 装备
- 阵营
- AI
- 战斗属性

这些全部由实际宿主实体决定。

角色资源只保存：

- 角色类型
- ID
- 显示名称
- 标签
- Home Story / 引用关系等已有资源元数据

## 3.2 角色类型

创建角色时选择：

- **个体**
- **集体**

### 个体角色

字段：

- `npc_id`
- `display_name`
- `tags[]`

规则：

- `npc_id` 在当前服务器/单机存档的 DGR 身份空间内唯一。
- 同时只能由一个宿主占用。
- 实体死亡、卸载、等待复活时不自动释放。
- 只有明确“解除指名”或“转移指名”时才释放/迁移。

### 集体角色

字段：

- `group_id`
- `display_name`
- `tags[]`

规则：

- 多个实体可以共享同一个 `group_id`。
- 一个实体可以同时属于多个 Group ID。
- Group ID 用于表达“这一群对象”。

示例：

- `npc_id=tavern_boss`：唯一酒馆老板。
- `group_id=guards`：一群卫兵。
- `group_id=slimes`：史莱姆群体。

# 4. NPC Identity Registry

## 4.1 唯一 NPC ID 禁止写入普通实体数据

**硬性约束：禁止把 NPC ID 序列化为宿主实体普通 NBT / CNPC Stored Data 中的可复制字段。**

由 DGR 服务端独立维护：

`npc_id -> host identity`

推荐以 DGR 自己的 SavedData / 服务端持久数据实现。

## 4.2 目标

- CNPC Cloner / 复制宝石复制 NPC 时，不可能复制 DGR 唯一 NPC ID。
- 其它模组复制实体时，不会制造第二个同 ID 宿主。
- DGR 自己的【复制器】与创造模式【收纳箱】也不需要做脆弱的“过滤 NPC ID NBT”。

## 4.3 生命周期

必须支持：

- 实体加载/卸载。
- 世界保存/重启。
- 实体死亡。
- CNPC 复活。
- 身份手动解除。
- 身份手动转移。

若某兼容模组的“复活”会创建新实体 UUID，则兼容层负责迁移原 NPC ID；不能释放后允许别人抢占。

# 5. Group ID 与实体归组

Group ID 与 NPC ID 不同：

- 不唯一。
- 可以复制。
- 同一实体可拥有多个 Group。
- DGR/CNPC 模板复制时允许继承 Group。

对原版/模组自然生成生物，应允许作者把一个明确实体类型整体归入某 Group。

UI 不使用“实体源”“成员规则”等抽象术语。推荐表现为：

- 仅当前实体加入该 Group
- 将此实体类型的所有实例加入该 Group

并直接显示实际实体类型标识。

对 DGR/CNPC 这类所有 NPC 共用同一底层实体类的情况，主要依靠：

- 手动归组
- 模板/Clone 继承 Group

# 6. 【物品】资源系统

## 6.1 Studio 不直接依赖 Forge 物品目录

0.3.1.0 不要求 Studio 读取：

- Forge Item Registry
- 客户端物品目录
- 某个存档背包
- 模组 jar

Studio 只管理 DGR 自己的【物品】身份。

## 6.2 物品类型

创建物品时：

- **个体**
- **集体**

### 个体物品

字段：

- `item_id`
- `display_name`
- `tags[]`

规则：

- Item ID 定义唯一。
- 世界中可同时存在任意数量匹配该 Item ID 的 ItemStack。
- Item ID 固定采用精确物品身份，不提供“模糊 Item ID”。

### 集体物品

字段：

- `group_id`
- `display_name`
- `tags[]`

规则：

- Group ID 可以包含多个不同物品。
- 同一物品可同时属于多个 Group。
- Group 用于匹配“某一类物品”。

示例：

- `item_id=royal_key`
- `group_id=sword`
- `group_id=weapon`
- `group_id=iron_sword`

# 7. 物品匹配语义

## 7.1 Item ID

Item ID 永远使用**精确身份**。

精确匹配应比较：

- 基础物品类型
- Metadata / Damage / 耐久
- 名称
- Lore
- 附魔
- NBT / 模组自定义数据
- 其它必要 ItemStack 数据

堆叠数量本身不作为“是否同一种物品”的身份依据。

## 7.2 Group ID 成员匹配方式

正式名称：

- **精确匹配**
- **模糊匹配**

UI 必须有 `?` 或说明文字。

### 精确匹配

> 只有基础物品、耐久/Metadata、名称、Lore、附魔及其它物品数据一致时才属于该 Group。适合剧情钥匙、特殊任务道具、特殊装备等。

### 模糊匹配

> 只匹配基础物品类型，忽略耐久、名称、Lore、附魔及其它物品数据。适合“任意铁剑”“任意苹果”等。

## 7.3 Group 可包含多个成员

例如 `group_id=sword` 可以加入：

- 木剑（模糊匹配）
- 石剑（模糊匹配）
- 铁剑（模糊匹配）
- 金剑（模糊匹配）
- 钻石剑（模糊匹配）
- 模组钢剑（模糊匹配）

同一把铁剑还可同时属于：

- `sword`
- `iron_sword`
- `weapon`

# 10. 【收纳箱】

## 10.1 适用范围

只对生物实体开放。

不支持：

- 玩家
- 掉落物
- 投射物
- 矿车/船等非生物实体（除非未来显式扩展）

## 10.2 生存模式

空箱右键生物：

- 捕获实体本体
- 实体从世界移除
- 完整数据进入收纳箱
- 若实体持有 NPC ID，身份继续被占用，不释放

已收纳箱右键方块：

- 恢复原实体
- NPC ID 继续属于该实体身份
- 收纳箱变为空置

## 10.3 创造模式

空箱右键生物：

- 原实体不移除
- 保存一个单槽实体模板

已收纳箱右键方块：

- 无限生成副本
- 收纳箱保持“已收纳”
- 复制 Group ID
- 不复制 NPC ID

## 10.4 贴图

- 空置：开盖木箱
- 已收纳：闭盖木箱

Tooltip 建议显示：

- 空置 / 已收纳
- 已收纳实体显示名称或类型

# 13. 故事包热更新

## 13.1 命令

0.3.1.0 必须支持类似：

`/dgr reload`

用于在线重新加载故事包。

## 13.2 事务式加载

推荐流程：

1. 扫描新版故事包
2. 解析
3. 验证
4. 验证通过后替换旧定义
5. 验证失败则保留旧定义
6. 输出明确错误信息

禁止：

- 先卸载旧定义，再尝试加载新包

## 13.3 玩家进度

普通 reload 不得自动清空玩家已有进度。

结构性不兼容修改若无法安全迁移：

- 必须安全失败 / 报告
- 不允许静默重置

- 会话重要选择/结果

- NPC Identity Registry
- Group 配置
- 世界实体配置
- 其它真正属于世界的数据

禁止把玩家任务进度放入全局世界状态。

## 15.1 从只读图谱升级为“跨故事逻辑接线层”

Story 节点继续由项目 Story 自动生成。

用户不能在 Story Graph 中创建：

- 会话
- 任务

用户可以：

- 连接 Story 暴露的 ◆ 逻辑输出

## 15.2 Story 内新增

- 【逻辑输入】
- 【逻辑输出】

每个【逻辑输入】映射为 Story Graph 上一个 ◆ 输入。

每个【逻辑输出】映射为 Story Graph 上一个 ◆ 输出。

端口必须使用稳定 `port_id`：

- 改显示名称不断线

# 17. ● 流程接口与 ◆ 逻辑接口

## 17.1 ● 流程接口

视觉：

- 圆形
- 蓝 / 青蓝
- 相对较粗

规则：

> 输出端最多一条连线；输入端允许多个来源。

口诀：

> **去向唯一，来源可多。**

## 17.2 ◆ 逻辑接口

视觉：

- 菱形
- 琥珀 / 金橙
- 与流程线明显区分

规则：

> 输出可被多个地方读取；一个输入最多只能有一个来源。

口诀：

> **来源唯一，去向可多。**

需要多个条件：

- 【与】
- 【或】
- 【非】

必须显式画出，不允许端口隐式 AND/OR。

# 18. 【开始】节点重构

## 18.1 定义

【开始】正式定义为：

> **故事启动方式节点**

特点：

- 没有 `●流程输入`
- 可以接受 `◆逻辑输入`
- 包含 1..N 条独立“启动方式”
- 每个启动方式拥有一个独立 `●流程输出`

## 18.2 启动方式

示例：

- 与某角色交互
- 进入某区域
- 某条件满足
- 未来其它事件型启动方式

某条启动方式可带一个 `◆` 条件输入。

复杂逻辑必须在画布中先通过【与】【或】【非】组合，再接入【开始】。

多个启动方式不需要额外 AND/OR 设置：

- 每个启动方式拥有自己的 ● 输出
- 后续如何汇合/分支由 Flow 连线决定

## 18.3 Story 外部逻辑接入

Story Graph 的 ◆ 输入进入 Story 后：

【逻辑输入】节点输出 ◆ → 接到【开始】某启动方式的 ◆ 条件输入。

“【开始】是最前面的节点”只意味着没有 `●` 前驱，不禁止 ◆ 状态源接入。

# 19. 【条件】节点

统一删除/替代旧：

- 【判断】
- 【条件触发器】

正式名称：

> **【条件】**

## 19.1 接口

输入：

- `● 流程输入`
- `◆ 逻辑输入`

输出：

- `● 是`
- `● 否`

## 19.2 统一运行语义

当 ● 到达：

1. 立即读取当前 ◆。
2. 若当前结果对应的 ● 出口已有连线：
   - 立即从该出口离开。
3. 若当前结果对应出口没有连线：
   - 节点保持等待。
   - 等待 ◆ 状态改变。
   - 一旦变为“存在已连接出口”的状态，则发出一次对应 ● 并结束本次等待。

因此：

- 是/否都连：即时 If 判断。
- 只连“是”：等待 true。
- 只连“否”：等待 false。

一旦从节点离开：

- 停止监听
- 不因未来状态变化重复发脉冲

两个出口都未连接：

- Studio 强警告/错误

# 22. 【目标】与【生效条件】

## 22.1 基础接口

每个【目标】：

- `0..N` 个可选 ◆【生效条件】输入
- `1` 个固定 ◆ 完成状态输出

没有生效条件时：

UI 显示：

> **默认激活**

语义：

> Task Active 后目标自动开始监控/统计。

## 22.2 多个生效条件

多个输入默认全部需要满足。

复杂 OR/NOT：

- 使用【或】【非】节点预组合
- 再接入【生效条件】

## 22.3 动态门控

生效条件只控制：

> 当前是否统计新的数据

不控制：

- 已有进度保存
- 已完成状态回退

例：夜晚击杀 10 史莱姆：

- 夜晚杀 7 → 7/10
- 白天 → 暂停统计，仍是 7/10
- 白天再杀 → 不计数
- 再入夜 → 从 7/10 继续
- 达到 10/10 → ◆完成=true

# 23. 【结算】

## 23.1 唯一节点

每个 Task 固定唯一【结算】。

## 23.2 可动态增加结果槽

用户可以：

- 增加
- 删除
- 命名
- 上下排序

每个槽：

- 一个 ◆ 输入
- 稳定 `port_id`
- 显示名称
- 排序

## 23.3 优先级

从上到下依次判断。

第一个为 true 的结果获胜：

- Task 结束
- 只产生一个外部 ● 流程输出
- 后续槽不再生效

全部 false：

- Task 保持 Active

## 23.4 映射

内部【结算】每个具名槽：

→ 外部聚合【任务】节点一个具名 ● 流程输出。

## 23.5 禁止中间状态滥用

【结算】只表示真正 Task 终局。

“未完成”“可交付”“隐藏目标完成”等中间状态：

- 使用【逻辑输出】
- 不放入【结算】
