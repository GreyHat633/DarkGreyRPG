# DarkGrey RPG Studio 2.1 Architecture

## Product boundary

Studio 2.1 is the WPF authoring application under `Studio/`. Its persisted RPG
resources are consumed by the Java 1.7.10 Runtime without an export or an
intermediate database. The older Godot authoring implementation remains in the
repository for the Phase 1–5 history, but it is not the Studio 2.1 executable.

The implementation is split into three explicit layers:

- `DarkGreyRPG.Studio.Core` owns project files, migration, validation, resource
  identity, Story membership, atomic writes, and editor-only graph layout.
- `DarkGreyRPG.Studio` owns the WPF shell, commands, navigation, resource
  editors, the free-form Story Flow canvas, and the derived Project Graph.
- `src/main/java/darkgrey/rpg` owns Runtime loading, player state, node
  execution, CustomNPC+ integration, commands, and Forge lifecycle behavior.

## Sources of truth

There is one source of truth for each concern:

- Actor, Dialogue, and Quest contents: their project-level JSON files.
- Story membership and Story metadata: the owning Story JSON.
- Runtime Story logic and node positions: `nodes` and `connections` in the
  Story JSON edited by Story Flow.
- Project Story Graph edges: derived from valid `EnterStory` nodes; never
  authored or saved independently.
- Project Graph visual positions only:
  `resources/editor/story-graph-layout.json`, ignored by Runtime.
- CustomNPC+ Actor binding: CNPC persistent stored data key
  `darkgrey_rpg.actor_id`.

This prevents Dialogue from owning Quest actions, Quest from owning an issuer,
and the Project Graph from becoming a second logic graph.

## Runtime vertical slice

Studio 2.1 adds Runtime support for `StoryStart`, `DialogueExitBranch`,
`EnterStory`, and `EndStory`, while retaining legacy node spellings and direct
Dialogue-result outputs. `PlayDialogue` records the named result; a following
`DialogueExitBranch` emits that name; `EnterStory` resets the current instance,
starts the target Story, and advances its entry during the same event with a
bounded transition depth.

`/dgrpg story start <id>` provides an operator entry point. `/dgrpg reload`
atomically replaces the Runtime snapshot only after the whole project validates.

## Persistence and failure behavior

Studio repositories use an atomic temporary-file validation/write boundary.
Open documents keep dirty and saved snapshots for undo/redo and close prompts.
Migration captures all affected original bytes, writes an E-drive project-local
backup, and attempts full rollback on any failure. Runtime reload retains the
previous snapshot when a candidate project is invalid.

`.tooling/2.1-acceptance/DarkGrey-2.1-Acceptance/`.
