# Studio 2.0 to 2.1 Migration

## When migration runs

`ProjectService.OpenProject` reads the project, runs `ProjectMigration`, and
then reopens the upgraded project. Migration is required when the project or an
Actor uses legacy schema v1, or when the generated `uncategorized` Story does
not contain the required legacy Actor ownership.

## Changes

- `project.json` becomes schema v2.
- Legacy Actors become schema v2 and receive
  `home_story_id: "uncategorized"` when no owner exists.
- `stories/uncategorized.json` is created or repaired and owns those Actors.
- Existing Story metadata, membership, Flow nodes, connections, and unknown
  supported legacy Runtime node types are retained.
- Dialogue and Quest schema v1 remain Runtime-readable; Studio saves edited
  resources as schema v2 with `display_name` and `home_story_id`.

## Safety

All candidate files are parsed before mutation. The migration captures the
original bytes and writes a timestamped backup under `.migration-backups/` in
the project. Every upgraded file is written through the atomic writer and
reparsed before replacement. If any step fails, the original snapshot is
restored and opening fails instead of presenting a partially migrated project.
`migration.log` records success or the attempted rollback but can never mask
the migration result.

## Compatibility

The Java Runtime accepts schema v1 and v2 editor fields. It also accepts legacy
Story type spellings and the new 2.1 snake_case nodes. Project Graph layout is
under `resources/editor/` and is intentionally ignored by Runtime.

Before migrating a production project, keep the generated backup until both
Studio save/restart and `/dgrpg reload` have been accepted. To roll back, close
Studio and restore the affected files from the latest `.migration-backups`
directory as a set.
