# DarkGrey_RPG 0.3.0.0 Architecture Freeze

## Baseline

- Source baseline: commit `9be86aa`, containing Studio 2.1.3 and Runtime 0.5.0.
- Development branch: `codex/0.3.0.0-flow-first-authoring`.
- The product version becomes `0.3.0.0`; JSON schema versions remain independent.
- Existing user work in `examples/phase4_project` and untracked planning files is
  outside this implementation package and must remain untouched.

## One graph language, three scopes

| Scope | Authority | Interface kinds |
| --- | --- | --- |
| Story Flow | Story execution, resource calls, actions, transitions | flow and logic |
| Session graph | Lines, choices, local conditions, named exits | flow and logic |
| Task graph | Objectives, activation, Boolean composition, settlement | logic only |

All three scopes use the same UI-independent graph connection model and the same
editor gestures. Scope policies decide which node types and interface kinds are
allowed; they do not define different connection systems.

## Canonical persisted connection

```json
{
  "from_node_id": "node_a",
  "from_port_id": "port_x",
  "to_node_id": "node_b",
  "to_port_id": "port_y",
  "interface_kind": "flow"
}
```

Port identity is `(node_id, port_id)`. `display_name` and `order` may change
without rewriting connections. Duplicate/reference operations preserve or renew
IDs according to the resource identity rules, never according to labels.

## Connection invariants

| Interface | Output cardinality | Input cardinality |
| --- | --- | --- |
| flow | at most one target | multiple sources |
| logic | multiple consumers | at most one source |

A connection is valid only when both nodes and ports exist, the source is an
output, the target is an input, and both ports match `interface_kind`. A duplicate
edge is invalid. Adding a logic edge that would form a directed logic cycle is
invalid. Flow cycles are not rejected by Graph Core.

## Compatibility boundary

Phase 1 adds the canonical model beside the 2.1.3 `StoryConnectionResource`
rather than mutating legacy files in place. Story, Dialogue, and Quest migration
belongs to Phase 6 and must provide read-only preview, `.migration-backups`, a
transactional write, a log, and complete rollback. Runtime adoption begins only
after the canonical schema and Studio serializers are locked by tests.

## Scope policies

Graph Core defines three explicit scopes:

| Scope | Allowed interfaces | Required unique nodes |
| --- | --- | --- |
| Story Flow | flow and logic | Start |
| Session | flow and logic | Start |
| Task | logic only | Activate and Settle |

The policy layer validates a `GraphDocument` after generic graph validation. It
rejects a node type not registered for the selected scope, every flow port or
flow connection in a Task graph, missing required unique nodes, and duplicate
instances of a unique node. Required unique nodes are also non-deletable editor
contracts. Legacy Jump is loadable in Session compatibility mode but is not a
normally creatable node.

The initial canonical node registry uses stable persisted type IDs:

- Story Flow: `start`, `terminate`, `session`, `task`, `condition`, `and`,
  `or`, `not`, `action`, and `enter_story`.
- Session: `start`, `line`, `choice`, `condition`, `and`, `or`, `not`,
  `logic_output`, `end`, plus compatibility-only `legacy_jump`.
- Task: `activate`, `objective`, `and`, `or`, `not`, `logic_output`, and
  `settle`.

## Aggregate boundary projection

Boundary projection is deterministic and UI-independent. It never matches a
display label and never allocates a replacement ID for an existing boundary.

Session aggregate ports are:

- fixed flow input `flow_in`;
- fixed logic input `logic_in` (the connection is optional, the port is not);
- flow outputs projected from Session `end` boundaries;
- logic outputs projected from Session `logic_output` boundaries.

Task aggregate ports are:

- fixed flow input `flow_in`;
- flow outputs projected from ordered Task settlement slots;
- logic outputs projected from Task `logic_output` boundaries.

Every dynamic aggregate output preserves the boundary `port_id`, display name,
order, and interface kind. Projection rejects blank IDs/names, duplicate IDs,
duplicate display names across all public outputs, a reserved fixed-port ID, or
a boundary with the wrong kind. Rename and reorder therefore update aggregate
presentation while existing Story connections remain addressed to the same ID.

Saving a canonical Session or Task first analyzes every Story placement bound
by ordinal-exact `resource_id` and the matching aggregate kind. The plan is
detached and fail-closed for malformed/ambiguous placements or for graph/edge
drift between analysis and apply. Compatible stable IDs preserve their edges.
Removed or same-ID retyped ports enumerate all affected external connections;
the UI must display that list and obtain explicit confirmation before applying
all placement replacements and edge cleanup as one Story Undo unit.

The derived Story synchronization is applied before the child repository write.
If that durable write fails, the host rolls back only the derived edit and
restores Undo/Redo state displaced by it. On success, the child editor becomes
clean while the Story editor remains dirty, so persistence of the derived Story
change is still an explicit user action rather than an implicit second write.

## Shared editor endpoint and wire contract

The existing WPF `FlowPortControl` remains a compatibility class while the
editor is migrated. Its effective connection identity is `PortId` with legacy
`PortName` fallback; its visible label is `DisplayName` with the same fallback.
Changing only the label never changes an endpoint ID.

A wire target is eligible before document mutation only when:

- both effective port IDs are non-empty;
- endpoints belong to different nodes;
- one endpoint is input and the other is output;
- both endpoints have the same `GraphInterfaceKind`.

Scope/cardinality/cycle validation remains a second Core check. UI endpoint
eligibility never replaces Graph Core validation.

One shared WPF style source defines connection presentation:

- flow: cyan/blue, 3 DIP normal stroke;
- logic: amber/gold, 2 DIP normal stroke;
- selected connections may increase contrast/thickness without changing kind;
- automation text states Flow or Logic semantics.

Legacy Story Flow ports default to Flow, so adopting stable IDs and shared
styles does not rewrite 2.1.3 Story JSON.

## Graph edit transaction contract

The shared editor uses a UI-independent edit session over `GraphDocument`.
Candidate validation is narrower than whole-document validation: unrelated
Problems elsewhere in a repairable draft do not block a valid local edit.

Before a connection mutation, the candidate validator checks:

- source/target node and port existence and uniqueness;
- output-to-input direction and matching interface kind;
- duplicate edge rejection;
- flow-output and logic-input cardinality after excluding any edge being
  atomically reconnected;
- Task scope's complete Flow prohibition and node-level allowed kinds;
- whether a new Logic edge would create a directed cycle.

Connect, disconnect, reconnect, port-label rename, and port reorder are atomic
Undo units. A failed connect/reconnect changes neither the document nor Undo
history. Reconnect removes the original only in a candidate snapshot, validates
the replacement, and commits both operations together. Rename/reorder preserves
`port_id` and every connection endpoint. Undo/Redo restores full graph snapshots
and clears Redo after a new successful edit.

## Dynamic port edit contract

Dynamic-port capability is determined by `(scope, node type, direction, kind)`;
it is not persisted as a mutable flag on each port and cannot be granted by a
display label. Phase 1 supports these canonical roles:

- Story `start`: Flow outputs, minimum one;
- Story/Session/Task `and` and `or`: Logic inputs, minimum two;
- Session `choice`: paired Flow and Logic outputs, minimum one option; both
  roles are changed only through its semantic options editor;
- Task `settle`: Logic inputs, minimum one.

Every added port receives a new opaque `port_id`; labels and order remain
presentation metadata. IDs are compared ordinally and are never recycled by an
Undo branch. Add rejects blank/duplicate IDs, blank/duplicate labels within the
node, the wrong role, and an order already occupied by another dynamic port.

Remove rejects fixed or last-required ports. If a port has incident edges, the
default operation returns those references without mutation. A caller may
explicitly confirm removal with incident-edge cleanup; port removal and all
edge removals then form one Undo unit. Failed add/remove commands change neither
the document nor history. Undo/Redo uses the same isolated snapshots as other
graph edit commands.

Session Choice is the semantic exception to generic dynamic-port commands. Its
Core edit surface adds, renames, reorders, and removes one option together with
the option's `flow_port_id` Flow output and `option_id` Logic state output.
Stable IDs and existing connections survive label/order changes. Removing a
referenced option reports references until explicitly confirmed, then removes
both output kinds and their edges in one Undo unit; the final option cannot be
removed.

## Shared WPF graph command bridge

The WPF graph interaction layer addresses an endpoint only by node ID, port ID,
direction, and interface kind. It normalizes input-first and output-first drags
to the same canonical connection and performs the shared endpoint compatibility
check before calling `GraphEditSession`.

The same bridge handles new connect, either-end reconnect, explicit disconnect,
drop-on-blank disconnect for an existing wire, and Undo/Redo. A blank drop from
a new wire is a no-op. UI-ineligible or Core-invalid completion changes neither
the graph nor history and exposes validation issues to the host.

Story, Session, and Task hosts must use this bridge rather than implement their
own cardinality, cycle, or Task-Flow rules. Phase 1 proves this shared command
path with scoped fixtures; replacing the legacy 2.1.3 resource/view-model host
remains incremental and does not silently rewrite its JSON.

## Canonical graph host projection

One WPF host ViewModel adapts `(GraphDocument, GraphScope)` to bindable node,
ordered input/output port, and connection collections. It owns exactly one
`GraphEditSession` and one `GraphEditorCommandBridge`; Story, Session, and Task
must not receive separate host implementations.

Every successful command refreshes the projection from the canonical document.
Refresh preserves bindable node identity when a node ID remains unique, while
port and connection identity remains canonical `(node_id, port_id)` data rather
than label or collection position. Invalid or ambiguous draft data is projected
without crashing so Problems can still be repaired through local edits.

The host publishes validation issues from the command surface that performed the
last operation. Bridge-owned connection operations and direct session-owned
dynamic-port operations therefore cannot overwrite one another with stale
preview state during projection refresh.

Every canonical node also owns an explicit `properties` JSON object. Graph Core
keeps it deliberately untyped; scope-specific definitions provide typed schemas
without weakening the shared document model. Property keys use ordinal identity
and serialize in ordinal order, nested JSON values are cloned at every document,
history, and host-projection boundary, and set/remove operations are atomic Undo
units. The WPF projection exposes a read-only snapshot rather than the live
mutable dictionary.

Canonical node definitions add immutable fixed-port templates and top-level
property metadata beside that untyped bag. A registry-backed factory creates a
fresh fixed node shape, cloning every port and default JSON value. Pure Flow and
pure Logic definitions constrain their allowed interface kinds at the same
source of truth. The fixed-shape factory deliberately does not invent dynamic
slots. Minimum Start, Choice, And/Or, and Settle slots remain owned by semantic
initialization; the safe authoring service currently initializes And/Or and the
frozen Session Choice option contract, while unresolved Start/Settle schemas
stay fail-closed.

The same definitions own trimmed, non-blank author-facing names and stable
categories for all 27 scoped node types. Authoring queries preserve canonical
registry order while excluding compatibility-only types such as Session
`legacy_jump`. Factory calls use the definition name when the caller omits or
passes a blank display name, so a new fixed shape does not expose a raw type key
as its default label.

An opt-in `GraphNodeShapeValidator` checks a node or whole graph against those
definitions without changing legacy Scope/CRUD behavior yet. It validates fixed
port identity/direction/kind, permits only registered non-fixed dynamic roles,
enforces their minimum counts, and checks required property JSON kinds while
allowing unknown extension properties. Fixed display names/order remain author
presentation state. Dynamic minima explicitly exclude fixed port identities.

`GraphNodeAuthoringService` is the non-mutating entry point for safe author
creation candidates. Fixed-only definitions use the registry factory; Story,
Session, and Task And/Or receive exactly two opaque, ordered Logic inputs.
Session Choice receives one default option with distinct opaque `option_id` and
`flow_port_id`, one Flow output, and one Logic state output. Story Start and
Task Settle remain fail-closed until their semantic initializers exist. Every
candidate must pass shape validation; the service checks identity and unique-
type conflicts first and never mutates the supplied graph.
Session End and Logic Output candidates also receive a non-blank opaque public
`port_id` at creation; only their localized `display_name` is intended for
ordinary Inspector editing. Reserved aggregate input IDs and IDs already used
by another Session public boundary are rejected before a candidate is returned.

## Parallel canonical resource envelope

The first 0.3.0.0 persistence boundary is a new strict canonical graph-resource
envelope beside, not inside, the 2.1.3 Story/Dialogue/Quest schemas. Its root
contract contains only `schema_version`, `resource_kind`, `id`, `display_name`,
and `graph`. `resource_kind` is exactly `story`, `session`, or `task` and maps to
one `GraphScope`; the adapter must reject a kind/scope mismatch. Version 1 of
this envelope rejects unknown root members and does not silently deserialize a
legacy resource.

This common envelope intentionally does not invent trigger, choice, settle,
objective, journal, membership, layout, or metadata containers. Those schemas
remain node/resource-specific work. Legacy conversion is a later explicit
migration with preview and backup; opening an old Story, Dialogue, or Quest is
not evidence that a canonical resource was loaded.

`GraphResourceRepository` persists exactly one expected resource kind in an
explicit caller-supplied directory. The repository deliberately does not choose
the future project folder layout. IDs are filename-safe stable identities;
filename/ID mismatch, wrong kind, malformed or legacy data, and path-like IDs
fail closed. New creation and existing replacement are separate operations,
and writes use the shared staged validation plus atomic replacement boundary.
Returned resources are detached snapshots.

Canonical Story membership is a separate schema-version-1 manifest rather than
an extra graph-envelope or legacy Story-v2 field. Its strict root is
`schema_version`, `story_id`, `owned_resources`, and `referenced_resources`;
each membership object contains exactly `actors`, `sessions`, and `tasks` ID
arrays. IDs compare ordinally, must be filename-safe stable identities, cannot
repeat within a list, and cannot be both owned and referenced in the same kind.
Array order is persisted but remains presentation-neutral. Loading a resource
never changes membership implicitly; future drag/reference commands require the
plan's explicit confirmation flow.

`CanonicalStoryMembershipRepository` atomically persists those manifests in an
explicit caller-supplied directory. Create and Replace are distinct;
filename/story_id mismatch, malformed/legacy data, invalid path-like IDs, and
failed staged writes fail closed without changing an existing manifest.

The canonical project store freezes its isolated layout under
`resources/canonical/`: `stories/`, `sessions/`, `tasks/`, and `memberships/`.
Construction and inspection are read-only; directory creation is explicit.
Legacy top-level `stories/`, `dialogues/`, and `quests/` remain outside this
store and are never scanned or converted implicitly.

The Java Runtime now has a separate immutable canonical content boundary for
that same layout. `CanonicalGraphResourceLoader` and
`CanonicalStoryMembershipLoader` reject malformed schema, kind, filename,
scope, graph, membership, and identity data without writing any path.
`CanonicalProjectContentLoader` returns an empty snapshot when the canonical
root is absent, but once the root exists it requires all four directories and
validates Story/membership pairing, member existence, and globally unique
Actor/Session/Task ownership. `ProjectRepository` loads that content only after
the shared Actor registry and installs it in `ProjectSnapshot` as part of the
existing atomic reload. A canonical failure therefore keeps the last accepted
legacy and canonical snapshot together.

`CanonicalSessionRuntime` is now a separate deterministic execution slice over
one canonical Session resource. It enforces the single Session Start
`flow_out` plus `logic_out`, pauses on Line/Choice, records stable selected
`option_id` values, completes through one named End, and snapshots/restores its
detached cursor state. Choice shape validation requires each option's
`flow_port_id` Flow output and `option_id` Logic output. Start activation,
Choice selection states, And/Or/Not, Condition branches, and stable public Logic
outputs are evaluated as one deterministic DAG; unconnected Logic inputs are
false and Logic outputs may fan out. Edge kind/direction, single-source Logic
inputs, Logic cycles, and Flow output cardinality fail closed. Snapshot state
contains the Choice-node selection trajectory, latest per-Choice selections,
internal Logic values, public outputs, activation input, cursor, status, and End
result; contradictory, stale, unknown, or incomplete state is rejected. Project
or Story orchestration, network/UI integration, and real Minecraft acceptance
remain later Stage 3 work. Runtime validation also
requires End and Logic Output `port_id` and `display_name` values to be unique
across the complete public Session boundary and rejects the reserved aggregate
input IDs `flow_in` and `logic_in`.

`CanonicalSessionInstanceStore` now owns the server-neutral invocation boundary
for that runtime. One player UUID plus Story ID retains at most one unconsumed
cursor, identified by its Story aggregate placement, Session resource, and a
positive transport ID which is never reused across persisted restarts. Every
Line/Choice action is fenced by player, Story, transport ID, and current node.
Completion retains exactly one End result and the detached public Logic output
map until explicit consumption.

The schema-version-1 NBT root persists both the complete detached runtime state
and `next_transport_id`. Its codec rejects unknown/missing/wrongly typed fields,
invalid UUID/status/boolean values, duplicate identities/maps, and active IDs
which are not below the next counter. Resource resolution and runtime restore
finish for the whole batch before the live store and counter are replaced, so a
late malformed or missing resource cannot partially install restart state.
`CanonicalSessionSavedData` now binds that store to the overworld
`MapStorage` under `darkgrey_rpg_canonical_sessions`. NBT is decoded and
validated before resolver binding, but the exact raw compound remains pending
until every referenced Session resource can be restored atomically. A missing
resource therefore leaves a retryable pending payload instead of replacing it
with an empty store. Successful mutations mark the data dirty; exception paths
also compare the complete pre/post store state so a runtime transition to
`FAILED` is persisted, while rejected stale or forged actions that changed
nothing remain clean. Public start and lookup results are detached snapshots or
immutable steps rather than the live store/runtime.

This is Forge storage integration and restart evidence, not Story execution or
real Minecraft client/server acceptance. Canonical packet handlers and the GUI
are described below and remain code/probe evidence until exercised in-game.

The canonical Session wire contract is separate from the legacy Dialogue
packets. A client action carries only the positive transport ID, Story ID,
current node ID, explicit Continue/Choice kind, and—only for Choice—the stable
`option_id`; player identity remains server-derived and choices are never sent
as array indices. Server frames preserve Story/resource/node identity and
ordered stable option IDs. Line frames require a speaker and no choices, while
Choice frames require no speaker and at least one option. Close frames contain
only transport and Story identity: End ports and public Logic outputs stay on
the server for Story execution rather than being exposed as chat results.

The DTO probes prove strict, immutable codec behavior, including UTF-8 byte
limits, malformed/truncated/trailing data rejection, and duplicate option
protection. Forge registration now retains legacy discriminator IDs 0-4 and
adds canonical Action, Frame, and Close at IDs 5-7 on their required sides.

`CanonicalSessionServerService` now forms the server-neutral orchestration and
presentation boundary. Before starting or resuming it resolves the exact Story
aggregate placement, its `resource_id`, Session membership, and every Line
speaker against that Story's owned/referenced Actor membership. It supplies the
trusted player UUID to `CanonicalSessionSavedData`, projects active Line/Choice
steps into stable-ID wire frames, and projects completion into a client-only
Close plus a detached server-only result containing the unique End port and
public Logic snapshot. Completion is deliberately not consumed here; the later
Story layer remains the only owner of that transition. Dispatches defensively
copy the mutable `IMessage` DTOs, and restart/FAILED/drift paths fail closed.

`CanonicalSessionForgeManager` derives the trusted player from the server
message context, reloads the current project snapshot, binds overworld
`CanonicalSessionSavedData`, and routes exactly one Frame or Close produced by
the server service. The Action handler schedules that work on the server main
thread; Frame and Close handlers likewise schedule client state changes on the
Minecraft thread.

The client uses a separate `GuiCanonicalSessionScreen` and a detached
`CanonicalSessionClientModel`; it does not reuse the legacy Dialogue screen.
Frame replacement is fenced by transport, Story, Session resource, and node
identity. Choice buttons retain stable `option_id` values, input stays disabled
while waiting for the server, and Close can dismiss only the matching
transport/Story screen. The client never displays or infers the server-only End
or Logic result.

Focused client-model and pure Forge-routing probes cover defensive DTO copies,
identity fences, stable option actions, and exclusive Frame-versus-Close
routing. This is code/probe evidence only: Story result consumption, live packet
exchange, GUI interaction, Dedicated Server, and real Minecraft client
acceptance remain later Stage 3 integration.

An operator-only acceptance entry is now wired through the existing `/dgrpg`
command: `session play <story_id> <aggregate_node_id>` starts the exact canonical
aggregate placement, while `session resume <story_id>` reprojects a persisted
active or completed instance. Both require a server-side player, derive its UUID
inside the Forge boundary, reuse the current project snapshot plus overworld
SavedData, and route exactly one Frame or Close. They do not expose or consume
the completion result. Canonical Story IDs and Session placement IDs are sorted
for deterministic tab completion.

The command is an acceptance/debug entry, not a substitute for Story Start
triggers or Story Flow orchestration. Focused seams prove the real server service
start/resume projection and retained completed state without constructing a
Minecraft process; a real player, network, GUI, and Story continuation remain
separate evidence gates.

`CanonicalStoryWorkspaceLoader` resolves one canonical Story and its strict
membership into a detached, presentation-neutral snapshot. The Story envelope
and membership are required roots and fail closed; member Actor, Session, and
Task IDs retain owned/referenced provenance and manifest order. A missing member
remains in the result and publishes a stable error Problem while other requested
members continue loading. Actor resolution addresses only the requested ID and
does not scan unrelated Actor files or any legacy Dialogue/Quest root.

The Story-first ViewModel accepts that snapshot directly. Resolved tree items
retain owned/referenced provenance; unresolved items keep their manifest
position, select into an explicit missing-resource Inspector state, and cannot
open a fabricated graph editor. Loader Problems remain available at the
workspace boundary for later shell publication.

When a Session Line node is selected, its speaker is authored through a
non-editable selector populated from that Story workspace's resolved Actor
items. The selector displays author-facing names while persisting only the
stable Actor ID through the shared graph host. A stored ID missing from the
current membership remains visible as an unresolved placeholder and is not
silently cleared. Project Actors outside the current Story are intentionally
excluded until the explicit confirm-then-reference membership workflow exists.

`CanonicalGraphResourceSaveCoordinator` is the durable boundary for an opened
canonical editor. It routes Story, Session, and Task snapshots to the matching
strict repository and advances the editor's saved baseline only after atomic
Replace and repository reload succeed. A clean editor is an explicit no-write
operation; multi-resource Save All semantics remain deferred.

Node add/remove operations are Core transactions. Add requires a caller-supplied
complete node, validates only the candidate and affected scope identities, and
clones the node before insertion. Remove reports detached incident-edge copies
and fails closed until referenced cleanup is explicitly confirmed; confirmed
cleanup is one Undo unit. Unknown or wrong-scope nodes remain deletable so a bad
draft can be repaired, while canonical required/non-deletable nodes stay
protected.

Editor positions are host layout state, not new canonical Graph JSON fields.
Phase 1 may assign deterministic fallback positions and preserve supplied layout
through projection refresh. Persistent layout schema and layout-aware Undo are
separate editor-metadata work and are not implied by the graph transaction
history implemented so far.

## Canonical WPF graph visual host

One `CanonicalGraphEditorView` and one `CanonicalGraphNodeControl` render the
host projection for all three scopes. Nodes and ports are materialized from
stable IDs, Flow and Logic wires use the shared style source, and malformed
unresolvable endpoints are omitted without changing the document.

Node and connection selection are transient, mutually exclusive view state.
Node selection survives a projection rebuild only when its non-blank ID is
still unique in the document; a missing host, removed node, blank ID, or
duplicate ID clears it. Delete gives an existing connection priority, then
routes node removal through the host transaction. Referenced and protected
nodes therefore fail closed and keep their selection plus Problems evidence;
referenced cleanup requires an explicit confirmation argument.

The visual host owns transient selection, pan/zoom, wire-draft, and node-position
state. Direct port drags are always new connections, including legal Logic
fan-out and Flow-input multi-source cases. Only an explicit existing-wire hit
supplies an original edge to the reconnect transaction. Hit proximity selects
the endpoint being moved; the opposite original endpoint anchors the draft and
remains fixed. Wrong-direction drops fail closed rather than replacing the
opposite end.

The typed `Host` dependency property is authoritative. Optional DataContext
adoption is tracked separately so a recycled implicit context can clear safely
without an unrelated shell DataContext overwriting an explicit Host binding.
Keyboard focus is placed on the graph canvas so Escape and Delete follow the
same routed command path used by deterministic tests.

Blank-canvas right-click builds one registry-backed `添加节点` menu for all
three scopes. Category and item order follow canonical definition order,
compatibility-only nodes are absent, and currently unsafe semantic roles are
visible but disabled. A menu click requests one opaque node ID, builds a
detached candidate through `GraphNodeAuthoringService`, commits it through the
typed host, stores the click position in host layout metadata, and selects the
new node. Failed creation neither retries the ID source nor changes graph JSON,
layout, or selection. Node, port, and connection right-click hits cannot inherit
the blank-canvas menu.

`CanonicalGraphResourceEditorViewModel` is the workspace seam between a
detached `GraphResourceDocument` and the shared host. Successful canonical graph
commands advance a monotonic host revision and raise `GraphChanged`; previews,
failed commands, projection refresh, and layout-only movement do not. The
adapter derives dirty state from canonical envelope content, exposes shared
Undo/Redo and Problems, and advances its saved baseline only after an explicit
`MarkSaved`. Persistence receives a detached envelope snapshot. This does not
claim persistent editor layout: node movement remains host-only metadata.

`CanonicalStoryWorkspaceViewModel` is the parallel Story-first navigation
state. Story Flow is the default and persistent home graph. Resource folders
are Actor, Session, and Task; expanding a folder never changes the middle
workspace. Single-click selection changes Inspector state only. Session/Task
replace the middle graph only through an explicit open action, and the
two-element breadcrumb returns to the same Story editor instance. Local editor
instances are retained across navigation, with a shell-supplied leave gate for
unsaved changes. This state layer does not yet replace the live legacy XAML.

`CanonicalStoryWorkspaceView` projects that state as one reusable three-column
control: expandable resource folders, the active canonical graph with
breadcrumb, and a selection-driven Inspector. Graph node, connection, and clear
selection events are routed through the workspace instead of creating a second
editor state. Session Line text, Choice prompt/options, End display names, and
Logic Output display names edit the same host-backed canonical document. Choice
option add/rename/reorder/remove uses the paired Flow/Logic semantic transaction;
the Inspector never offers either stable option or port ID as an editable field.
Referenced option removal first fails closed through Problems, then the WPF
boundary asks for explicit confirmation before retrying the same atomic Core
transaction. Actor activation remains selection-only;
Session/Task double-click or Enter is explicit local-graph activation. Replacing
the typed Workspace dependency property rebinds the shared graph host.

`CanonicalStoryDiscoveryService` reads the union of canonical Story-envelope
and membership filenames without consulting legacy Story data or creating
directories. Each present root is loaded through its strict repository.
Complete roots return detached data; a missing, malformed, or identity-mismatched
root keeps its filename-derived Story ID visible with stable Problems evidence
instead of aborting discovery of unrelated Stories.

Project Home merges legacy and canonical discovery by ordinal Story ID. A
canonical-only Story is independently selectable; a same-ID pair appears once
with canonical display/overview data and canonical opening precedence. The
Project Graph projection and Story lifecycle both give that canonical identity
precedence. Deleting a same-ID pair through the canonical branch removes only
the canonical roots and owned canonical resources; the legacy Story remains
visible and can be handled later through the unchanged legacy command.

The live shell probes the selected Story ID's canonical Story envelope and
membership paths. If neither exists, legacy behavior is unchanged. If either
exists, both strict roots must load before the canonical workspace replaces the
legacy center surface; incomplete or invalid canonical state fails closed with
Problems evidence, clears any prior clean canonical workspace, and never
invokes an implicit conversion. The live canonical surface hides the global
legacy resource browser while retaining its saved user preference for
restoration on exit.

Save Current routes the active Story, Session, or Task editor through
`CanonicalGraphResourceSaveCoordinator`. Dirty canonical editors block graph
switching and shell navigation until individually saved. Save All is disabled
for this workspace because a cross-file transactional persistence contract has
not been defined. The mount is covered by build and automated shell lifecycle
tests, but still requires separate real-window canonical interaction acceptance.

`CanonicalStoryResourceLifecycleService` owns the Core mutation boundary for
canonical Session and Task resources. Creation writes a minimum scope-valid
blank graph and then appends an owned membership; reference add/remove changes
only the selected Story manifest. Removing a broken reference does not require
the missing resource file, so the workspace can repair unresolved membership.

Owned deletion first enumerates every other canonical membership and blocks on
both references and unexpected duplicate ownership. Create/delete operations
compensate ordinary in-process failure so a failed second file operation does
not leave the first mutation accepted. Restoration uses an independent atomic
writer and validates the exact resource identity. This is deliberately not a
claim of crash-durable multi-file atomicity.

The live Story workspace now exposes Session/Task Create, Reference, and
Delete actions beside the Story title and through equivalent folder/item
context menus. Tree selection determines the kind; selecting or expanding a
folder does not replace the active graph. The Workspace ViewModel routes intent
only, while Shell owns dirty-editor blocking, dedicated canonical dialogs,
Core lifecycle calls, Problems/status reporting, and detached workspace reload.

Reference deletion is membership-only and may repair a missing target. Owned
deletion displays cross-Story blockers and requires an explicit destructive
confirmation; missing owned targets stay fail-closed. The dedicated dialogs
use `会话`/`任务` labels and clear filtered-out selections.

`CanonicalStoryActorLifecycleService` applies the same explicit membership
commands to the project-level Actor repository under `actors/`; Actors are not
copied into `resources/canonical/`. Creating an owned Actor stores the
canonical Story ID as `home_story_id`, while adding/removing a reference changes
only the canonical membership. A missing referenced Actor can still be removed
from membership so broken state remains repairable.

Owned Actor deletion scans every other canonical membership plus legacy Story
owned/reference lists. A legacy owned entry whose Story ID equals the canonical
owner is the migration-created mirror of that owner and is ignored; a same-ID
legacy reference and every different-ID legacy membership remain blockers.
Before the shared Actor file is deleted, Shell asks `ProjectService` to release
any clean cached Actor document; a dirty cached document fails closed. The Core
delete still provides ordinary in-process compensation only, not crash-durable
multi-file atomicity. Actor edits whose Home Story is canonical are persisted
through the strict canonical ownership manifest rather than incorrectly
requiring a same-ID legacy Story.

`CanonicalStoryLifecycleService` owns canonical Story creation and deletion.
Create writes a minimum scope-valid Story Flow containing the required `start`
node plus an empty same-ID membership manifest; failure of the second write
compensates the first. Its read-only deletion plan deterministically lists
owned Actors/Sessions/Tasks, retained referenced resources, incoming canonical
`enter_story` transitions, and stable blockers. Missing or malformed owned
files, conflicting canonical/legacy memberships, invalid graphs, ambiguous
nodes, and incoming transitions fail closed.

Delete recomputes the plan and snapshots every target byte before removing the
canonical Story, membership, and owned resources. An ordinary mid-delete
failure restores and validates every snapshot byte-for-byte; this remains
in-process recovery rather than a crash-durable transaction. Shell confirms
the exact owned-resource list, rejects a dirty open canonical workspace,
releases each owned Actor cache before mutation, and refreshes the Project Home
union afterward. Referenced resources and a same-ID legacy Story are never
deleted by the canonical branch.

`CanonicalAggregateNodeFactory` is the only initializer for bound Story Flow
`session` and `task` nodes. A placement stores the child resource identity in
required `resource_id` and projects current public boundaries: Session `end`
nodes become Flow outputs, Session/Task `logic_output` nodes become Logic
outputs, and Task `settle` result slots become Flow outputs. The candidate is
detached until the Story host accepts it. Generic canvas authoring is disabled
for both aggregate types, and projected output roles are shape-valid but
read-only in `GraphEditSession`, preventing manual drift from the child graph.
Every Session placement also contains fixed `flow_in` and `logic_in`; the
`logic_in` connection is optional and represents activation of Session Start's
single `logic_out` path.

The canonical resource tree starts an in-process Link drag only for resolved
Session/Task items already present in the current Story membership. The active
target must be Story Flow and the pointer must be inside the graph viewport;
viewport coordinates are transformed through the shared pan/zoom controller
before the host atomically adds and positions the candidate. Actor, missing,
foreign, local-graph, and invalid-position drops fail without consuming graph
state. Because this tree contains only current members, this slice performs no
membership mutation; a future global resource source must implement the plan's
confirm-then-reference sequence rather than copying resources.

`CanonicalProjectStoryGraphService` is the UI-independent source for canonical
Project Story Graph derivation. It consumes the strict canonical Story
discovery union without initializing the store, accepts only exact
`enter_story` nodes with string `target_story_id`, aggregates transitions by
source/target Story IDs, and retains source node/port identities for navigation.
Missing/invalid targets, malformed or globally ambiguous node IDs, incomplete
roots, isolation, and cycles remain deterministic diagnostics; no graph or
membership file is mutated.

The existing WPF Project Graph merges this snapshot with legacy-only Story
nodes. A same-ID canonical Story owns that identity and its legacy transitions
are not projected. Canonical-only Stories and edges use the same read-only
pan/zoom/layout surface, and precise Problems/edge navigation returns to the
canonical Story Flow and selects the source node. Isolation and cycle warnings
are recomputed over the displayed projection, while Project Graph continues to
offer layout edits only, never logic edits.

`CanonicalStorySessionCompletionRouter` is the pure Stage 3 boundary between a
completed Session and its caller Story. It revalidates the current Project
snapshot's Story, Session resource, and exact membership before resolving the
selected stable End port to one Flow successor. It also projects an exact,
ordered, immutable map of aggregate Logic outputs.

`CanonicalSessionSavedData` persists the integration boundary as one strict
world-state wrapper containing active/completed Session snapshots and pending
Story continuations. Accepting a completed result revalidates it against one
Project snapshot, removes that Session, and installs exactly one immutable
continuation for the same player/Story in one synchronized `WorldSavedData`
mutation. The continuation retains the aggregate placement, Session resource,
non-reusable transport ID, selected End port, exact next Story node/port, and
detached public Logic values. Exact replay is idempotent; any conflicting
continuation, Session/continuation identity overlap, or attempt to start another
Session for that player/Story fails closed. Legacy direct Session NBT remains
readable and migrates to the wrapper on the next write. This is the persisted
handoff required by the Stage 3 gate, not a claim that the downstream Story
cursor already executes: consuming/acknowledging the pending continuation and
running its target belongs to Stage 5 Story Flow runtime.

## Persisted mid-flow event waits and migration boundary

Canonical Story Flow owns two event-wait placements: `interact_actor` with an
exact `actor_id`, and `enter_region` with an exact finite sphere descriptor.
Both are ordinary single-cursor flow nodes with fixed `flow_in` / `flow_out`;
neither is a StoryStart trigger. Reaching one records the wait kind and payload
in the Story snapshot and world NBT. Actor interaction or periodic player
position first attempts to resume the sole matching active cursor; only when no
cursor matches may the same event participate in ordinary StoryStart matching.
Ambiguous matching waits fail closed and clean active child state.

Legacy `ActorInteract` / `EnterRegion` migration preserves this boundary. Safe
payloads are cloned without numeric coercion, unknown or conflicting fields are
reported as migration issues, and the source project is never rewritten. The
project transaction is available only after a read-only preview and explicit UI
confirmation; it creates a complete verified backup before absent-only atomic
canonical writes and retains the legacy resources for compatibility discovery.

## Explicitly rejected designs

- Task-local flow ports, sessions, entry/return nodes, and reward actions.
- Implicit AND/OR on a multi-source logic input.
- Implicit execution fan-out or multiple Story execution cursors.
- Junction/reroute nodes or a Task-specific editor and wiring language.
- Editable Project Story Graph logic.
- User-facing expression strings used in place of visible logic ports.
